# 문제 해결 기록

버그를 고칠 때마다 증상 → 원인 → 해결 순서로 간단히 남긴다. 자세한 코드 설명은 `docs/features/`에 둔다.

## 표 편집기에서 Tab 을 누르면 오른쪽에 셀이 있는데도 바로 아래 행으로 내려감 (2026-10-07)

**증상**: 표 편집기 셀에서 Tab 을 누르면 같은 행의 오른쪽 셀로 가지 않고 항상 아래 행의 첫 번째 셀로 갔다(사용자 제보).

**원인**: 요청이 "Tab 을 누르면 셀 옆의 행/열을 삭제하는 `[−]` 가 아니라 아래 행의 첫 번째 셀로 이동되도록"이었다. 원래 문제는 **행의 마지막 셀에서** Tab 이 `[−]` 버튼으로 가는 것이었는데, 이 문장을 "Tab 은 어느 열에서 누르든 아래 행의 첫 셀"로 문자 그대로 읽어서 만들었다. 오른쪽 셀로 가는 동작은 요청에 적혀 있지 않았지만 당연한 전제였다. 애매한 문장이었는데 확인 없이 한쪽으로 정했고, 시험도 같은 오해를 그대로 옮겨 적어서("어느 열에서 눌러도 첫 셀") 오해를 못 잡았다.

**해결**: Tab 을 "오른쪽 셀 → 행의 끝이면 아래 행의 첫 셀 → 마지막 행의 끝이면 새 행"으로 바꿨다(`src/lib/tableNav.js`의 `tabTarget`). 병합에 가려진 칸은 건너뛴다. Tab 만 바꾸면 Shift+Tab 이 `[−]` 로 가는 어긋남이 남아서 Shift+Tab 도 반대로 맞췄다(`shiftTabTarget`).
재현 테스트: `tests/lib/tableNav.test.js` (신고된 증상을 되돌리면 5개가 실패함을 확인). 실제 화면에서 3열 표로 `(0,0) → (0,1) → (0,2) → (1,0)`, 마지막 행 끝에서 새 행, Shift+Tab 역방향을 확인했다.
**교훈**: 키 동작처럼 해석이 갈릴 수 있는 요청은 "어디서 누르든 / 행 끝에서만" 같은 갈림길을 사용자에게 한 줄로 확인하거나, 만든 뒤 구체적인 이동 경로를 예로 적어 확인받는다.

## 코드블록에서 `NAME` 을 치면 `E` 로 END·ERD·ELSE 가 추천됨 (2026-10-07)

**증상**: ```` ```MySQL ```` 블록에서 `SELECT NAME` 까지 치면 추천 팝업에 END, ERD, ELSE, ENUM, ENGINE, EXISTS, EXPLAIN 이 떴다. 후보가 전부 `E` 로 시작했다(사용자가 스크린샷으로 알려 줌).

**원인**: 추천 팝업은 고정 트리거 글자 없이 "커서 앞 줄 끝의 모든 접미사"(`NAME`, `AME`, `ME`, `E`)를 긴 것부터 시험해서 앞부분이 같은 상용구가 있는 첫 길이에서 멈춘다. 앞의 셋은 걸리는 게 없고 마지막 `E` 한 글자가 `E…` 로 시작하는 키워드에 걸렸다. 접미사가 **단어의 시작 위치인지**는 보지 않았다.
한국어 단축어는 조사가 붙어 단어 중간에서 시작하는 일이 흔해서 만든 규칙인데, 키워드 147개를 상용구로 넣자 코드에서 드러났다.

**해결**: 코드블록 안에서만 접미사의 시작이 단어 중간이면(앞 글자와 시작 글자가 둘 다 글자·숫자·밑줄) 건너뛰도록 했다(`src/lib/snippetMatch.js`의 `findSnippetQuery` 옵션 `wordStartOnly`). 기호로 시작하는 상용구(`->`)는 글자 바로 뒤여도 찾는다. 글(문단)은 예전 그대로다.
재현 테스트: `tests/lib/snippetMatch.test.js`의 "wordStartOnly" (해결 코드를 끄면 3개가 실패). 같은 뿌리의 문제가 스페이스바 자동 치환(`findExactSnippetMatch`)에도 있다 — 제목이 줄 끝과 "끝이 같기만 하면" 단어 중간이어도 치환 대상이 된다. 키워드 묶음은 본문이 제목과 같아서 해가 없고, 이번에는 고치지 않았다.

## 대소문자만 다른 상용구(`MYSQL` / `mysql`)를 같이 등록할 수 없음 (2026-10-07)

**증상**: `MYSQL` → `MySQL` 상용구를 만든 뒤 `mysql` → `MySQL` 상용구를 만들면 `mysql` 은 목록에 나타나지 않았다. 에디터의 자동 치환도 대소문자를 구분하지 않았다.

**원인**: 두 가지가 겹쳤다. (1) 상용구는 "단축어 = 파일 이름"인데 **Windows 는 파일 이름의 대소문자를 구분하지 않아서** `mysql.md` 가 이미 있는 `MYSQL.md` 와 같은 파일로 취급됐다. 등록 함수가 "파일이 이미 있으면 그걸 쓴다"로 동작해서 `mysql` 의 본문이
`MYSQL` 파일에 **덮어써졌고**, 목록에는 파일 하나(`MYSQL`)만 남았다. (2) 에디터가 상용구를 찾을 때 양쪽을 소문자로 바꿔 비교해서 대소문자 구분 자체가 불가능했다.

**해결**: 같은 폴더에 대소문자만 다른 이름이 이미 있을 때만, 새 단축어의 영문자를 `%XX` 로 인코딩해서 저장하도록 했다(`electron/fileSystem.js`의 `ensureSnippet`). 평소에는 이름을 그대로 써서 예전 파일과 호환된다. 에디터의 정확 일치(스페이스바 자동 치환·Alt+Enter)는 대소문자를
구분하도록 바꿨다(`src/lib/snippetMatch.js`). 추천 팝업은 대소문자를 가리지 않되 같은 대소문자를 앞에 보여 준다. 재현 테스트: `tests/electron/snippetCase.test.js`(해결 코드를 끄면 13개 중 10개가 실패하는 것을 확인함 — Windows 가 아닌 곳에서는 충돌이 없어 이 시험이 원래부터 통과한다).
이미 덮어써진 `MYSQL` 의 본문은 복구되지 않으므로 `mysql` 은 새로 등록해야 한다.

## 편집창 아래 여백을 칸 높이만큼 주면 textarea 가 칸 밖으로 삐져나옴 (2026-10-07, 출시 전에 발견)

**증상**: 편집창 아래로 더 스크롤할 수 있게 `padding-bottom: 100cqh`(편집 칸 높이만큼)를 줬더니, 실제 글 영역(textarea)의 높이가 칸보다 24px 커졌다. 미리보기(1280x720)에서 잰 값은 `칸 573.2px` / `textarea 597.2px`.

**원인**: textarea 는 위·아래 여백의 합(24px + 칸 높이)보다 작아질 수 없다. `inset: 0` 으로 칸 높이에 맞추려 해도 여백 합이 더 크면 그 합이 높이가 된다. 그 결과 아래쪽 24px 가 칸 밖으로 나가고 끝까지 스크롤해도 마지막 줄이 예상보다 24px 아래에 남았다.

**해결**: 아래 여백을 `calc(100cqh - 24px - 1px)`(칸 높이에서 위 여백과 1px 을 뺀 값)로 바꿨다. 잰 값으로 `칸 573.2px = textarea 573.2px`, 글 영역과 배경판의 스크롤 길이·위치가 같고, 끝까지 내리면 마지막 줄이 편집창 맨 위 줄 자리에 온다.
자세한 설명: `docs/features/editor-scroll-past-end.md`.

## 상용구 단축어 `*`가 `_`로 바뀌어 저장됨 (2026-10-07)

**증상**: `*` 를 `※` 로 바꾸는 상용구를 만들려고 단축어에 `*` 를 넣고 등록하면, 목록에 단축어가 `_` 로 나왔다. `?` `:` `"` 등도 같았다.

**원인**: 상용구는 "단축어 = 파일 이름"(`.wikidesk-snippets/카테고리/단축어.md`)으로 저장된다. Windows 는 파일 이름에 `* ? : / \ " < > |` 를 못 쓰기 때문에,
저장 직전에 이 글자를 전부 `_` 로 바꾸는 공용 함수(`sanitizeFileName`)를 거쳤다. 되돌릴 방법이 없는 변환이라 읽을 때도 파일 이름이 그대로 단축어가 되어 `_` 로 보였다. 더 나쁜 점은 `*` 와
`?` 처럼 서로 다른 단축어가 같은 `_.md` 로 겹쳐서, 나중에 등록한 것이 앞의 것을 **조용히 덮어썼다**는 것이다.

**해결**: 상용구 파일 이름만 되돌릴 수 있는 방식으로 바꿨다(`electron/fileSystem.js`의 `encodeSnippetFileName`/`decodeSnippetFileName`) — 못 쓰는 글자와 `%` 를 `%XX`(16진수)로 저장하고
읽을 때 되돌린다. `*` 는 `%2A.md` 로 저장되고 화면에는 `*` 로 보인다. 이미 `_.md` 로 저장돼 있던 예전 상용구는 그대로 `_` 로 남으므로(어느 글자였는지 알 수 없어서) 지우고 다시
등록해야 한다. 재현 테스트: `tests/electron/fileSystem.test.js`의 "상용구 단축어에 파일 이름에 못 쓰는 글자가 들어가는 경우".

## 주인공 폴더 이름을 두 번째로 바꾸면 등장인물의 "00" 문서가 안 따라감 (2026-10-03)

**증상**: 작품 폴더의 `주인공` 폴더를 `유성호`로 바꾸면 `등장인물/00 주인공`이 `00 유성호`로 같이 바뀌는데, 이어서 `유성호`를
`민준`으로 바꾸면 `00 유성호`가 그대로 남았다.

**원인**: "이름을 바꾸는 폴더가 정확히 `주인공`인가"로 연동 대상을 판별하고 있었다. 한 번 바꾸고 나면 폴더 이름이 더 이상 `주인공`이
아니라서 그 뒤로는 연동이 일어나지 않았다. 코드 주석에는 "몇 번을 바꿔도 계속 따라간다"고 적어 뒀지만 사실과 달랐다. 자동 테스트
(`tests/store/fileOperations.test.js`)를 만들다가 이 경우를 그대로 옮겨 적었더니 바로 실패해서 발견했다.

**해결**: 폴더 이름이 아니라 "같은 작품 폴더의 `등장인물` 안에 `00 <바꾸기 전 폴더 이름>` 문서가 실제로 있는가"로 판별하도록
바꿨다(`src/store/useAppStore.js`의 `renameFile`). 작품 폴더(소설/웹툰/만화 밑) 바로 아래 폴더일 때만 적용되고, 짝이 되는 문서가
없으면(지웠거나 직접 이름을 바꿔 뒀으면) 아무것도 하지 않는다.

## 편집 모드 제목 강조 배경이 엉뚱한 줄에 겹쳐 보임 (2026-10-02)

**증상**: 편집 모드에서 `=제목=` 줄에 배경을 얹어 강조하는 기능(`docs/features/app-icon-taskbar.md`와 무관, 에디터 전용 기능)을 켜 두면,
가끔 강조 배경이 실제 제목 줄이 아니라 그 아래 몇 줄(본문 내용)까지 겹쳐서 칠해져 보였다. 스크롤을 위로 올렸다가 다시 내리면 정상으로 돌아왔다.

**원인**: 편집기는 실제 글자를 그리는 `<textarea>` 뒤에 똑같은 텍스트를 보이지 않게 겹쳐 그리는 배경판(div)을 두고, 그 배경판에서만
제목 줄에 색을 칠하는 방식으로 구현돼 있다. 두 요소는 서로 다른 DOM이라 스크롤 위치(`scrollTop`)를 따로 들고 있는데, 지금까지는
`textarea`에서 실제 `scroll` 이벤트가 발생할 때만 배경판의 스크롤을 맞춰 줬다. 그런데 글자를 입력해서 내용 길이가 바뀌면(특히 커서를
따라 `textarea`가 자동으로 스크롤될 때) 배경판 쪽 `scrollHeight`가 그 순간 아직 새 내용 기준으로 다 안 커져 있어서 `scrollTop`을
제대로 못 따라가고 멈춰버리는 경우가 있었다. 수동으로 스크롤하면 그제서야 `scroll` 이벤트가 다시 발생해 둘이 맞춰졌다.

**1차 해결(불완전)**: 편집 중인 글(`text`)이 바뀔 때마다(탭 전환 포함) 화면에 그려진 직후 배경판의 스크롤 위치를 `textarea`의 그
순간 실제 스크롤 위치로 강제로 다시 맞추는 처리를 추가했다(`src/components/EditorPane.jsx`). 그런데 실제로는 재발했다 — 스크롤
위치를 맞추는 것만으로는 부족했는데, 두 요소의 **총 높이 자체가 서로 달라서** 같은 `scrollTop` 값이 서로 다른 줄을 가리키고
있었기 때문이다(아래 정정 참고).

**정정 — 진짜 원인**: 배경판에서 제목 줄은 한 줄 전체 너비로 배경을 칠하려고 `display: block`인 `<span>`으로 그리는데, 그 span
**안에** 줄바꿈 문자(`\n`)를 같이 넣고 있었다. `white-space: pre-wrap`에서는 이 줄바꿈이 span 내부에 "내용 뒤에 남는 빈 줄"을 하나
더 만들어서, 제목 span 하나가 실제로는 2줄 높이(제목 1줄 + 보이지 않는 빈 줄 1줄)를 차지하고 있었다. 제목이 아닌 일반 줄은 span이
`inline`이라 이 문제가 없다(그 줄바꿈이 다음 줄 내용과 같은 흐름을 공유해서 빈 줄이 안 생김). 그 결과 제목이 나올 때마다 배경판
전체 높이가 `textarea`보다 한 줄씩 더 쌓였고, 문서 위쪽에서는 거의 안 보이다가 아래로 스크롤할수록(제목을 더 많이 지날수록) 어긋남이
점점 커져 강조 배경이 실제 제목보다 몇 줄 아래(본문 내용)에 겹쳐 보였다.

**해결**: 제목 줄의 줄바꿈 문자를 그 span **밖으로** 뺐다 — `display: block` 요소는 어차피 앞뒤로 자동으로 줄 경계가 생기므로
문자로 된 줄바꿈이 따로 필요 없고, 안에 넣으면 오히려 위 문제가 생긴다. 수정 후 배경판과 `textarea`의 `scrollHeight`가 정확히
일치함을 확인했다(`src/components/EditorPane.jsx`의 `renderHighlightLines`).
