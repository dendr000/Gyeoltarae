# 문제 해결 기록

버그를 고칠 때마다 증상 → 원인 → 해결 순서로 간단히 남긴다. 자세한 코드 설명은 `docs/features/`에 둔다.

## 상용구 단축어 `*`가 `_`로 바뀌어 저장됨 (2026-10-07)

**증상**: `*` 를 `※` 로 바꾸는 상용구를 만들려고 단축어에 `*` 를 넣고 등록하면, 목록에 단축어가 `_` 로 나왔다. `?` `:` `"` 등도 같았다.

**원인**: 상용구는 "단축어 = 파일 이름"(`.wikidesk-snippets/카테고리/단축어.md`)으로 저장된다. Windows 는 파일 이름에 `* ? : / \ " < > |` 를 못 쓰기 때문에,
저장 직전에 이 글자를 전부 `_` 로 바꾸는 공용 함수(`sanitizeFileName`)를 거쳤다. 되돌릴 방법이 없는 변환이라 읽을 때도 파일 이름이 그대로 단축어가 되어 `_` 로 보였다. 더 나쁜 점은 `*` 와
`?` 처럼 서로 다른 단축어가 같은 `_.md` 로 겹쳐서, 나중에 등록한 것이 앞의 것을 **조용히 덮어썼다**는 것이다.

**해결**: 상용구 파일 이름만 되돌릴 수 있는 방식으로 바꿨다(`electron/fileSystem.js`의 `encodeSnippetFileName`/`decodeSnippetFileName`) — 못 쓰는 글자와 `%` 를 `%XX`(16진수)로 저장하고
읽을 때 되돌린다. `*` 는 `%2A.md` 로 저장되고 화면에는 `*` 로 보인다. 이미 `_.md` 로 저장돼 있던 예전 상용구는 그대로 `_` 로 남으므로(어느 글자였는지 알 수 없어서) 지우고 다시
등록해야 한다. 재현 테스트: `tests/electron/fileSystem.test.js`의 "상용구 단축어에 파일 이름에 못 쓰는 글자가 들어가는 경우".

## 주인공 폴더 이름을 두 번째로 바꾸면 등장인물의 "00" 문서가 안 따라감 (2026-10-03)

**증상**: 작품 폴더의 `주인공` 폴더를 `유성호`로 바꾸면 `등장인물/00 주인공`이 `00 유성호`로 같이 바뀌는데, 이어서 `유성호`를
`민준`으로 바꾸면 `00 유성호`가 그대로 남았다.

**원인**: "이름을 바꾸는 폴더가 정확히 `주인공`인가"로 연동 대상을 판별하고 있었다. 한 번 바꾸고 나면 폴더 이름이 더 이상 `주인공`이
아니라서 그 뒤로는 연동이 일어나지 않았다. 코드 주석에는 "몇 번을 바꿔도 계속 따라간다"고 적어 뒀지만 사실과 달랐다. 자동 테스트
(`tests/store/fileOperations.test.js`)를 만들다가 이 경우를 그대로 옮겨 적었더니 바로 실패해서 발견했다.

**해결**: 폴더 이름이 아니라 "같은 작품 폴더의 `등장인물` 안에 `00 <바꾸기 전 폴더 이름>` 문서가 실제로 있는가"로 판별하도록
바꿨다(`src/store/useAppStore.js`의 `renameFile`). 작품 폴더(소설/웹툰/만화 밑) 바로 아래 폴더일 때만 적용되고, 짝이 되는 문서가
없으면(지웠거나 직접 이름을 바꿔 뒀으면) 아무것도 하지 않는다.

## 편집 모드 제목 강조 배경이 엉뚱한 줄에 겹쳐 보임 (2026-10-02)

**증상**: 편집 모드에서 `=제목=` 줄에 배경을 얹어 강조하는 기능(`docs/features/app-icon-taskbar.md`와 무관, 에디터 전용 기능)을 켜 두면,
가끔 강조 배경이 실제 제목 줄이 아니라 그 아래 몇 줄(본문 내용)까지 겹쳐서 칠해져 보였다. 스크롤을 위로 올렸다가 다시 내리면 정상으로 돌아왔다.

**원인**: 편집기는 실제 글자를 그리는 `<textarea>` 뒤에 똑같은 텍스트를 보이지 않게 겹쳐 그리는 배경판(div)을 두고, 그 배경판에서만
제목 줄에 색을 칠하는 방식으로 구현돼 있다. 두 요소는 서로 다른 DOM이라 스크롤 위치(`scrollTop`)를 따로 들고 있는데, 지금까지는
`textarea`에서 실제 `scroll` 이벤트가 발생할 때만 배경판의 스크롤을 맞춰 줬다. 그런데 글자를 입력해서 내용 길이가 바뀌면(특히 커서를
따라 `textarea`가 자동으로 스크롤될 때) 배경판 쪽 `scrollHeight`가 그 순간 아직 새 내용 기준으로 다 안 커져 있어서 `scrollTop`을
제대로 못 따라가고 멈춰버리는 경우가 있었다. 수동으로 스크롤하면 그제서야 `scroll` 이벤트가 다시 발생해 둘이 맞춰졌다.

**1차 해결(불완전)**: 편집 중인 글(`text`)이 바뀔 때마다(탭 전환 포함) 화면에 그려진 직후 배경판의 스크롤 위치를 `textarea`의 그
순간 실제 스크롤 위치로 강제로 다시 맞추는 처리를 추가했다(`src/components/EditorPane.jsx`). 그런데 실제로는 재발했다 — 스크롤
위치를 맞추는 것만으로는 부족했는데, 두 요소의 **총 높이 자체가 서로 달라서** 같은 `scrollTop` 값이 서로 다른 줄을 가리키고
있었기 때문이다(아래 정정 참고).

**정정 — 진짜 원인**: 배경판에서 제목 줄은 한 줄 전체 너비로 배경을 칠하려고 `display: block`인 `<span>`으로 그리는데, 그 span
**안에** 줄바꿈 문자(`\n`)를 같이 넣고 있었다. `white-space: pre-wrap`에서는 이 줄바꿈이 span 내부에 "내용 뒤에 남는 빈 줄"을 하나
더 만들어서, 제목 span 하나가 실제로는 2줄 높이(제목 1줄 + 보이지 않는 빈 줄 1줄)를 차지하고 있었다. 제목이 아닌 일반 줄은 span이
`inline`이라 이 문제가 없다(그 줄바꿈이 다음 줄 내용과 같은 흐름을 공유해서 빈 줄이 안 생김). 그 결과 제목이 나올 때마다 배경판
전체 높이가 `textarea`보다 한 줄씩 더 쌓였고, 문서 위쪽에서는 거의 안 보이다가 아래로 스크롤할수록(제목을 더 많이 지날수록) 어긋남이
점점 커져 강조 배경이 실제 제목보다 몇 줄 아래(본문 내용)에 겹쳐 보였다.

**해결**: 제목 줄의 줄바꿈 문자를 그 span **밖으로** 뺐다 — `display: block` 요소는 어차피 앞뒤로 자동으로 줄 경계가 생기므로
문자로 된 줄바꿈이 따로 필요 없고, 안에 넣으면 오히려 위 문제가 생긴다. 수정 후 배경판과 `textarea`의 `scrollHeight`가 정확히
일치함을 확인했다(`src/components/EditorPane.jsx`의 `renderHighlightLines`).
