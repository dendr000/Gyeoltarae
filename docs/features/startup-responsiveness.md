# 앱을 켤 때 창이 멈추는 문제 (상용구 수천 개)

## 한 줄 요약

상용구가 1만 개쯤 있을 때 앱을 켜면 **몇십 초 동안 클릭이 안 되고 창이 반투명해지며 "응답 없음 — 대기/닫기" 창이 뜨던 문제**를 고쳤다. 원인은 상용구 파일을 하나씩 읽느라 **메인 프로세스가 계속 바빴던 것**이다. 이제 상용구를 **100개씩 나눠 읽고 사이사이 숨을 쉬어서** 읽는 동안에도 창이 응답한다. 또 **문서를 저장할 때마다 상용구 전부를 다시 읽던 것**도 없앴다.

## 무엇이 느렸나 (실제로 잰 것)

| 항목 | 이 PC 의 실사용 작업 폴더(`D:\WikiDesk`) |
|---|---|
| 문서 | 281개, 합쳐서 0.6MB — 전부 읽는 데 약 30ms, 폴더 훑기 약 100ms |
| 분류·자료·틀·이미지 | 각각 수 ms |
| **상용구** | **10,453개** — 이것이 거의 전부다 |

- 상용구는 파일 하나가 아주 작지만 **개수가 1만 개**라서, 처음 읽는(캐시에 없는) 파일 하나에 수 ms 가 든다. 1만 개면 수십 초다.
- 예전 방식은 화면이 파일마다 "읽어 줘"(IPC)를 1만 번 보냈다. 메인 프로세스(창을 그리고 윈도 메시지를 받는 쪽)가 그 요청을 처리하느라 쉴 틈이 없어서 **윈도가 "응답 없음"으로 판단**했다.
- 시험(빌드한 exe, 새로 만든 파일 1만 개로 잰 값): 옛 방식은 앱을 켠 뒤 상용구 폴더가 사이드바에 나타나기까지 약 56초, 한 번에 몰아 읽는 방식을 잠깐 써 봤더니 **한 번의 호출이 80초 동안 메인을 통째로 멈춤**(더 나쁨). 지금 방식은 **메인이 가장 오래 멈춘 시간이 약 0.9초**(1초를 넘긴 적 없음)다.

## 고친 것

1. **100개씩 나눠 읽기** — 화면이 파일 100개를 한 번에 읽어 달라고(`files:readMany`) 하고, 받으면 한 틱 쉰 뒤 다음 100개를 요청한다. 한 번에 길게 멈추지 않으므로 창이 계속 응답한다. 읽는 동안 헤더 "저장됨" 옆에 진행 표시가 뜬다([snippet-load-indicator.md](snippet-load-indicator.md)).
2. **상용구가 아닌 색인을 먼저 내보내기** — 검색·문서 링크·분류 같은 것은 상용구 읽기가 끝나기를 기다리지 않고 바로 쓸 수 있다. 상용구는 그 뒤에 읽어 와서 채운다.
3. **저장할 때마다 상용구를 다시 읽지 않기** — 예전에는 문서를 저장할 때마다(파일이 바뀌었다는 알림이 올 때마다) 상용구 1만 개를 처음부터 다시 읽었다. 이제 **상용구 폴더(`.wikidesk-snippets`) 안의 파일이 바뀐 때만** 다시 읽는다.
4. **더 새로운 불러오기가 시작되면 옛 불러오기는 멈춤** — 읽는 도중 또 색인을 다시 만들면 옛 읽기는 다음 100개에서 멈추고 그 결과를 버린다(같은 파일을 두 번 읽거나 옛 결과가 새 결과를 덮지 않게).
5. **읽지 않을 폴더를 고르는 곳을 메뉴에 추가** — 메뉴 **설정 > 상용구 불러오기…** 를 누르면 상용구 창이 **폴더별 사용** 탭으로 열린다. 체크를 푼 폴더는 앱을 켤 때 아예 읽지 않는다([snippet-folder-toggle.md](snippet-folder-toggle.md)). 파이썬 강의를 듣는 동안 `Python`·`명령`·`영어`·`기호`만 체크하면 읽는 상용구가 약 550개로 줄어든다.

## 문서·폴더별 "불러오기" 체크는 만들지 않았다

"각 폴더/문서마다 불러오기를 끄는 체크"는 **지금은 효과가 거의 없어서** 만들지 않았다. 위 표처럼 문서 281개는 전부 읽어도 30ms 이고 느린 것은 상용구였다. 문서가 수만 개로 늘어서 실제로 느려지면 그때 만드는 것이 맞다(문서를 안 읽으면 검색·분류·문서 링크 기능이 그 문서를 놓치는 부작용도 있다).

## 구조

| 파일 | 역할 |
|---|---|
| `electron/fileSystem.js` (`readManyFiles`) | 파일 여러 개를 한 번에 읽는다(못 읽은 것은 `null`) |
| `electron/main.js`, `electron/preload.cjs` | `files:readMany` 채널, `onOpenSnippetLoad`(메뉴) |
| `src/lib/snippetLoad.js` (`loadSnippetEntries`) | 100개씩 나눠 읽고 사이마다 쉬며, 취소되면 멈춘다 — 순수 함수(읽기 함수를 받는다) |
| `src/store/useAppStore.js` | 상용구를 마지막에 읽기(`rebuildIndexes`), 번호로 옛 불러오기 버리기, `snippets: 'keep'` 옵션, 감시기 알림에서 상용구 폴더 변화 판별(`isSnippetPath`) |
| `electron/settingsMenu.js` | 메뉴 "상용구 불러오기…" |
| `tests/electron/snippetBatch.test.js`, `tests/electron/snippetLoadMenu.test.js` | 위 규칙과 메뉴 연결 시험 |

## 알아 둘 것·한계

- **읽는 총 시간은 크게 줄지 않는다.** 1만 개를 처음 읽는 데 드는 시간(디스크가 파일을 여는 비용)은 그대로이고, **그동안 창이 멈추지 않게** 한 것이다. 총 시간을 줄이려면 읽지 않을 폴더를 끄는 것이 가장 효과가 크다.
- 상용구 읽기가 끝나기 전에는 아직 읽지 못한 상용구가 추천 팝업에 나오지 않는다. 진행 표시가 있는 동안이다.
- 상용구 폴더를 **파일 탐색기에서 직접 고치면** 감시기가 알려서 그 폴더가 다시 읽힌다(이전과 같다). 상용구 폴더 밖의 변화(문서 저장 등)에는 다시 읽지 않는다.
- 위 시간은 개발 PC 에서 새로 만든 파일로 잰 값이고, 실제 디스크·백신 설정에 따라 다르다.

## 용어 설명 (초보자용)

| 용어 | 뜻 |
|---|---|
| 메인 프로세스 | 앱의 "본체". 창을 그리고 윈도가 보내는 메시지에 답한다. 이게 오래 바쁘면 창이 "응답 없음"이 된다 |
| IPC | 앱 안에서 화면과 본체가 서로 주고받는 요청. 1만 번 주고받으면 본체가 쉴 틈이 없다 |
| 응답 없음 | 윈도가 창이 일정 시간 메시지에 답하지 않으면 반투명하게 만들고 "대기/닫기"를 묻는 상태 |
| 나눠 읽기(chunk) | 한꺼번에 하지 않고 조금씩 나눠서 하는 것 |
