# 문제 해결 기록: 편집 모드(편집창·제목 강조·찾기·점프)

편집창, 제목 강조 배경, 줄 위치 계산, 찾기 칸에서 생긴 문제. 증상 → 원인 → 해결 순서로 남긴다. 전체 목차는 [`../troubleshooting.md`](../troubleshooting.md).

## 편집창 아래 여백을 칸 높이만큼 주면 textarea 가 칸 밖으로 삐져나옴 (2026-10-07, 출시 전에 발견)

**증상**: 편집창 아래로 더 스크롤할 수 있게 `padding-bottom: 100cqh`(편집 칸 높이만큼)를 줬더니, 실제 글 영역(textarea)의 높이가 칸보다 24px 커졌다. 미리보기(1280x720)에서 잰 값은 `칸 573.2px` / `textarea 597.2px`.

**원인**: textarea 는 위·아래 여백의 합(24px + 칸 높이)보다 작아질 수 없다. `inset: 0` 으로 칸 높이에 맞추려 해도 여백 합이 더 크면 그 합이 높이가 된다. 그 결과 아래쪽 24px 가 칸 밖으로 나가고 끝까지 스크롤해도 마지막 줄이 예상보다 24px 아래에 남았다.

**해결**: 아래 여백을 `calc(100cqh - 24px - 1px)`(칸 높이에서 위 여백과 1px 을 뺀 값)로 바꿨다. 잰 값으로 `칸 573.2px = textarea 573.2px`, 글 영역과 배경판의 스크롤 길이·위치가 같고, 끝까지 내리면 마지막 줄이 편집창 맨 위 줄 자리에 온다.
자세한 설명: `docs/features/editor-scroll-past-end.md`.

## 편집 모드 제목 강조가 문서 아래로 갈수록 한 줄에서 몇 줄씩 어긋남 (2026-10-12)

**증상**: 편집 모드에서 `=제목=` 줄에 칠하는 강조 막대가 제목 줄이 아니라 한 줄 위·아래, 심하면 몇 줄 떨어진 줄에 나타났다.
문서 위쪽에서는 맞고 아래로 갈수록(긴 줄이 많을수록) 더 벌어졌다. 2026-10-02 에 두 번 고쳤지만 재발했다(아래 항목).

**원인(미리보기에서 직접 재서 확정)**: 두 가지가 겹쳐 있었다.
1. **스크롤바 폭 차이.** 입력칸(`textarea`)은 항상 세로 스크롤바가 있어 글 영역이 15px 좁고(497px), 배경판은 `overflow: hidden` 이라
   스크롤바가 없어 글 영역이 더 넓었다(512px). 화면 너비에 닿는 긴 줄이 두 요소에서 **서로 다른 곳에서 접혀** 줄 수가 달라졌고, 그 뒤의
   모든 제목이 그 차이만큼 밀렸다. 줄 길이가 제각각인 문서에서 제목별 어긋남을 재 보니 0, 0, 1, 0, 25, 25, 25, 48, …, 121px 로
   **줄 높이(약 24px)의 배수로 쌓였다**(= 한 줄, 두 줄, … 다섯 줄).
2. **줄 높이가 소수.** `font: 14px/1.7` 은 줄 높이가 23.8px 이라, 두 요소가 서로 다른 방식(입력칸은 글 줄, 배경판은 제목 블록)으로
   소수를 쌓아 문서가 길수록 1~3px 씩 더 벌어졌다. 이쪽은 막대가 약간 위아래로 어긋나는 정도였다.

**해결**(`src/App.css`): 두 요소에 같은 값을 준다.
- `scrollbar-gutter: stable` — 둘 다 스크롤바 자리를 항상 같은 폭으로 비워 글 영역 폭(497px)이 같아졌다.
- 줄 높이를 정수 `24px`(`font: 14px/24px`) — 소수 누적이 없어졌다.
수정 뒤 줄 길이가 다른 문서 3종(제목 120개), 창 폭 1280px 와 900px(글 영역 307px, 긴 단어가 여러 번 접힘)에서 제목마다의 어긋남이
모두 같은 상수(프로브 기준 3px)이고 입력칸·배경판의 폭과 `scrollHeight` 가 일치함을 확인했다. 문서 깊은 곳(제목 36~38)도 화면으로 확인.

**재발 방지**: `tests/components/editorLayers.test.js` 가 두 규칙의 `font`·`padding`·`scrollbar-gutter` 가 같은 값인지, 줄 높이가
정수 px 인지 확인한다(레이아웃 자체는 브라우저에서만 잴 수 있어 CSS 값만 지킨다). 이 CSS 를 고친 뒤에는 미리보기에서 긴 줄이 섞인 문서를 만들어
입력칸과 `.editor-highlight-backdrop` 의 `clientWidth`·`scrollHeight` 가 같은지, 각 `.eline-heading`(0.86.0 이후 배경판의 제목 줄 block) 의 `offsetTop` 이
입력칸의 같은 제목 줄 위치(같은 폭의 숨은 거울 div 로 잼)와 일정한 간격인지 확인할 것.

**실사용 확인 (2026-10-13)**: 고친 뒤 실제 앱에서 편집 모드의 제목 강조가 제대로 작동하는 것 같다고 사용자가 확인했다("잘 작동하는 듯"). 같은 바탕 위에 만든 **줄 번호**와, 번호를 눌러 줄마다 켜는 **강조 점**(0.86.0, [editor-gutter.md](features/editor-gutter.md))도 의도대로 보인다고 했다. 줄 번호는 배경판의 논리 줄(`div.eline`)마다 CSS 카운터로 그리고, 점은 그 줄 위치를 믿고 누르는 영역을 잡으므로, 입력칸과 배경판의 줄 위치가 맞는다는 이 수정이 전제였다. 이 확인은 사용자의 눈으로 본 것이고 자동 테스트로 지키는 것은 아니다(테스트는 CSS 값 일치만 지킨다).

**교훈**: 2026-10-02 에는 "스크롤 위치"와 "제목 span 안의 줄바꿈 문자(`\n`)" 를 원인으로 보고 고쳤지만 증상만 줄었다. 막대가 "문서 아래로 갈수록 줄 단위로
쌓이며 어긋난다" 는 모양(= 줄 수가 달라지는 것)을 먼저 재서 두 요소의 **폭**을 비교했다면 바로 잡혔다. 겹쳐 그리는 방식은 폭·글꼴·여백·스크롤바·줄 높이가
한 가지라도 다르면 어긋난다.

## 편집 모드 제목 강조 배경이 엉뚱한 줄에 겹쳐 보임 (2026-10-02)

**증상**: 편집 모드에서 `=제목=` 줄에 배경을 얹어 강조하는 기능(`docs/features/app-icon-taskbar.md`와 무관, 에디터 전용 기능)을 켜 두면,
가끔 강조 배경이 실제 제목 줄이 아니라 그 아래 몇 줄(본문 내용)까지 겹쳐서 칠해져 보였다. 스크롤을 위로 올렸다가 다시 내리면 정상으로 돌아왔다.

**원인**: 편집기는 실제 글자를 그리는 `<textarea>` 뒤에 똑같은 텍스트를 보이지 않게 겹쳐 그리는 배경판(div)을 두고, 그 배경판에서만
제목 줄에 색을 칠하는 방식으로 구현돼 있다. 두 요소는 서로 다른 DOM이라 스크롤 위치(`scrollTop`)를 따로 들고 있는데, 지금까지는
`textarea`에서 실제 `scroll` 이벤트가 발생할 때만 배경판의 스크롤을 맞춰 줬다. 그런데 글자를 입력해서 내용 길이가 바뀌면(특히 커서를
따라 `textarea`가 자동으로 스크롤될 때) 배경판 쪽 `scrollHeight`가 그 순간 아직 새 내용 기준으로 다 안 커져 있어서 `scrollTop`을
제대로 못 따라가고 멈춰버리는 경우가 있었다. 수동으로 스크롤하면 그제서야 `scroll` 이벤트가 다시 발생해 둘이 맞춰졌다.

**1차 해결(불완전)**: 편집 중인 글(`text`)이 바뀔 때마다(탭 전환 포함) 화면에 그려진 직후 배경판의 스크롤 위치를 `textarea`의 그
순간 실제 스크롤 위치로 강제로 다시 맞추는 처리를 추가했다(`src/components/EditorPane.jsx`). 그런데 실제로는 재발했다 — 스크롤
위치를 맞추는 것만으로는 부족했는데, 두 요소의 **총 높이 자체가 서로 달라서** 같은 `scrollTop` 값이 서로 다른 줄을 가리키고
있었기 때문이다(아래 정정 참고).

**정정 — 진짜 원인**: 배경판에서 제목 줄은 한 줄 전체 너비로 배경을 칠하려고 `display: block`인 `<span>`으로 그리는데, 그 span
**안에** 줄바꿈 문자(`\n`)를 같이 넣고 있었다. `white-space: pre-wrap`에서는 이 줄바꿈이 span 내부에 "내용 뒤에 남는 빈 줄"을 하나
더 만들어서, 제목 span 하나가 실제로는 2줄 높이(제목 1줄 + 보이지 않는 빈 줄 1줄)를 차지하고 있었다. 제목이 아닌 일반 줄은 span이
`inline`이라 이 문제가 없다(그 줄바꿈이 다음 줄 내용과 같은 흐름을 공유해서 빈 줄이 안 생김). 그 결과 제목이 나올 때마다 배경판
전체 높이가 `textarea`보다 한 줄씩 더 쌓였고, 문서 위쪽에서는 거의 안 보이다가 아래로 스크롤할수록(제목을 더 많이 지날수록) 어긋남이
점점 커져 강조 배경이 실제 제목보다 몇 줄 아래(본문 내용)에 겹쳐 보였다.

**해결**: 제목 줄의 줄바꿈 문자를 그 span **밖으로** 뺐다 — `display: block` 요소는 어차피 앞뒤로 자동으로 줄 경계가 생기므로
문자로 된 줄바꿈이 따로 필요 없고, 안에 넣으면 오히려 위 문제가 생긴다. 수정 후 배경판과 `textarea`의 `scrollHeight`가 정확히
일치함을 확인했다(`src/components/EditorPane.jsx`의 `renderHighlightLines`).

**이후**: 이 수정으로도 긴 줄이 많은 문서에서 재발해서 2026-10-12 에 폭(스크롤바)과 줄 높이까지 맞췄다 — 위 항목 참고.

## 찾기 칸에 글을 치면 문서의 선택된 글이 덮어써짐 (2026-10-15)

**증상**: Ctrl+F(또는 Ctrl+Shift+F)로 찾기 칸에 글을 치면, 첫 글자에서 찾은 글이 편집창에서 선택되고 커서가 편집창으로 넘어갔다. 이어서 친 글자가 **문서의 선택된 글을 덮어썼다**(예: 문서의 "가"를 찾으려 "가나"를 치면 문서의 "가"가 "나"로 바뀜). Enter(다음 찾기)를 거듭 누르면 문서에 줄바꿈이 들어갔고, 바꿀 내용 칸에서 Enter 를 거듭 눌러도 두 번째부터 문서에 줄바꿈이 들어갔다.

**원인**: 찾은 글을 보여 주는 함수(`selectFindMatch`)가 `textarea.focus()` 를 불러 포커스를 편집기로 옮겼다. 포커스가 없는 입력칸은 선택 색이 그려지지 않아서 선택을 보이게 하려고 한 것으로 보이는데, 그 결과 찾기 칸에서 치던 글자가 편집기로 들어갔다. 바꾸기(`replaceRange`)도 글을 바꾸려고 편집기에 포커스를 줬고 돌려주지 않았다. 처음부터 있던 동작이다.

**해결**: 찾은 글을 보여 줄 때 포커스를 옮기지 않고, 현재 찾은 글은 편집기 뒤쪽 표시층(배경판)에 CSS 사용자 지정 강조(`::highlight(find-current)`)로 칠한다. 바꾼 뒤에는 포커스를 원래 입력칸으로 돌려놓는다. 규칙은 `src/lib/docFind.js`, 문서는 [doc-find-multiline.md](features/doc-find-multiline.md).

**어떻게 찾았나**: 줄바꿈 찾기를 만들며 실제 Electron 창에서 실제 키 입력(Shift+Enter 등)으로 확인하다가 발견했다. 브라우저 미리보기만으로는 화면 갱신이 멈춰 포커스 이동이 가려져서 놓치기 쉽다. 고친 뒤 같은 순서로 다시 확인했다(타이핑, Shift+Enter, Enter·Ctrl+Enter·F3, 바꾸기, 줄바꿈 모두 바꾸기와 Ctrl+Z 한 번).
