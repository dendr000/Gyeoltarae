# 문제 해결 기록: 창·포커스·시작 속도

창 포커스, 깜빡임, 시작 속도에서 생긴 문제. 증상 → 원인 → 해결 순서로 남긴다. 전체 목차는 [`../troubleshooting.md`](../troubleshooting.md).

## 켠 지 20~25초 뒤 글 입력이 멈춤 — 문서 1만 개 폴더 (2026-11-19)

**증상**: 실제 작업 폴더(문서 10,796개)로 앱을 켜고 0.25초마다 한 글자씩 70초 입력해 재 보니, 25초까지는 글자당 약 60ms 로 정상이다가 26~45초 사이에 멈췄다(한 글자에 최대 18.3초). 45~65초에는 간헐적으로 느렸고 65초 뒤에야 안정됐다. 입력 없이 반응만 재도 48초까지 0.3~2초씩 걸렸다.

**원인**: 폴더 감시기(chokidar)가 메인 프로세스 안에서 파일 1만 개를 훑었다. 입력이 계속되면 "20초가 지나면 켠다"는 상한(`maxWaitMs`) 때문에 입력 도중에 켜졌고, 훑는 동안 메인이 막혀 자동 저장·파일 읽기 요청이 줄을 섰다. (시작 속도 문제와 같은 뿌리이지만, 시작 때 겹치는 것을 피하는 방법으로는 상한에 걸린 경우를 못 막았다.)

**해결**: 감시기를 별도 작업 프로세스(`electron/watchWorker.js`, utilityProcess)로 옮겼다. 메인은 메시지만 전달한다. 감시를 끌 때는 프로세스가 끝난 뒤 진행한다.

**검증**: 고친 뒤 패키지한 exe 로 같은 시험 — 2·3회째 최대 지연 0.08초·0.07초, 150ms 넘는 입력 없음. 첫 실행은 0~60초에 글자당 0.3~0.8초 느렸으나 멈춤은 없었고 이후 재현되지 않았다(새 exe 첫 실행의 디스크 검사 추정, 확정은 아님). 외부에서 만든 문서가 30초 뒤에도 목록에 반영되는 것도 확인했다. 시험: `tests/electron/watchProcess.test.js`.

**교훈**: 시간 상한으로 "늦추는" 방법은 상한에 걸리면 같은 문제가 그대로 나온다. 무거운 일은 늦추지 말고 메인 프로세스 밖으로 옮긴다.

## 사이드바에서 문서를 누를 때마다 뒤에 있는 다른 앱(클로드 앱 등)이 깜빡이며 비침 (2026-10-12)

**증상**: 파일 트리·탭·사이드바 항목(분류·자료·상용구·틀)·뷰어의 링크를 누를 때마다, 결타래 창 뒤에 있는 다른 앱 창이 잠깐 앞으로 나왔다가 사라졌다.

**원인**: 이런 클릭 처리마다 `refocusWindow()` 를 불렀고, 메인 프로세스의 `refocusMainWindow()` 는 `mainWindow.blur()` 뒤에 `focus()` 를 한다. Windows 에서 `blur()` 는 z-순서상 **다음 창을 잠깐 활성화**해서 뒤의 앱이 비쳐 보였다. 이 호출은 "모달이 닫힌 직후 새 문서의 입력칸을 자동 포커스할 때 키 입력이 OS 에 전달되지 않던 문제(Windows 전용 Electron 버그)"를 풀려고 넣은 것인데, 그냥 클릭해서 여는 경우까지 모두 같은 호출을 쓰고 있었다. 이름 바꾸기 더블클릭에서 같은 증상으로 한 번 뺀 적이 있었다(`FileTree.jsx` 의 `beginRename` 주석).

**해결**: blur 없이 렌더러 포커스만 맞추는 `softRefocusWindow()`(`window:softRefocus`)를 새로 만들고, **클릭으로 여는 동작**은 모두 이것을 쓰게 바꿨다 — 파일 트리의 파일·폴더 클릭, 탭 전환, 분류·자료·상용구·틀 사이드바 항목, 뷰어의 위키 링크·분류 링크·자료 카드·`[편집]` 링크·분류 문서 목록·새로 만들기 버튼. 클릭했다는 것은 이 창이 이미 활성이라는 뜻이라 OS 포커스를 다시 맞출 필요가 없다. **모달이 닫힌 직후 새 문서를 자동 포커스하는 흐름**(새 문서·자료·틀 만들기, 프롬프트 창 열기, 빈 문서 편집기 자동 포커스, 이미지 이름 바꾸기, 상용구·사전 창의 저장)은 기존 `refocusWindow()` 를 그대로 둔다.

**검증과 한계**: `tests/electron/softRefocus.test.js` 가 클릭 처리 파일들에 blur 가 들어간 호출이 없는지, 가벼운 포커스 함수가 `blur()` 를 쓰지 않는지를 지킨다(변이 검사로 확인). 실제 깜빡임은 화면으로만 볼 수 있고 이 환경에서는 Electron 창을 직접 볼 수 없어서 **눈으로 확인하지는 못했다** — 앱을 다시 빌드해 실행한 뒤 사이드바에서 문서를 눌러 보고 깜빡임이 없는지 확인할 것. **내용이 비어 있는 문서**를 열 때는 편집기가 자동 포커스를 위해 기존 방식을 쓰므로 그때는 깜빡일 수 있다.

**교훈**: 포커스 문제를 `blur()` 로 푸는 방식은 눈에 보이는 부작용이 있다. 새로 포커스 보정을 넣을 때는 "정말 OS 포커스가 어긋나는 흐름(모달 직후, 비동기 뒤)"에만 쓰고, 일반 클릭에는 쓰지 않는다.

## 앱을 켜고 클릭할 수 있기까지 15초 가까이 걸림 (2026-10-14)

**증상**: exe 를 켜면 창은 뜨는데 무엇을 클릭할 수 있게 되기까지 15초쯤 걸렸다. 작업 폴더에 상용구 4천여 개(파일 4,259개)가 있을 때.

**원인**: 앱은 켜질 때 파일 4,222개를 하나씩(요청 4,222번) 읽어 색인을 만든다. 같은 때에 폴더 감시기(chokidar)도 켜졌고, 감시기는 켜자마자 작업 폴더의 파일 전부를 훑는다(단독 약 8~9초). 둘이 메인 프로세스의 같은 처리 줄을 써서 읽기 요청이 감시기 작업 뒤에 줄을 섰다. 측정: 읽기만 0.4초, 감시기와 겹치면 약 10초. 나머지 몇 초는 Electron 이 켜지는 시간이다(측정하지 않음).

**해결**: 감시기를 켜는 시점을 미뤘다. 화면이 첫 색인을 끝내고 알리면, 사용자가 3초 입력하지 않는 틈(최대 20초 대기)에 켠다. 삭제·이름 바꾸기·이동 뒤에 다시 켜는 것도 같은 규칙이다. 규칙은 `electron/watchScheduler.js`, 자세히는 [startup-watch.md](features/startup-watch.md).

**남은 확인**: 고친 exe 로 실제 시작 시간을 사용자가 확인해야 한다(측정은 작업 폴더를 읽는 스크립트로만 했다).
