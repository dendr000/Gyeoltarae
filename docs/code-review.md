# 전체 코드 리뷰 — 오류 가능성 점검

- 작성일: 2026-09-15
- 범위: `electron/`, `src/` 전체 (백엔드 IPC/파일시스템, 렌더러 상태관리, 위키 파서, 컴포넌트)
- 방식: 파일 전체를 직접 읽으면서 점검. 이번 리뷰에서 실제로 고친 것과, 고치지 않고 기록만 해둔 것을 구분해서 정리함.

## 1. 이번에 실제로 고친 것

### 1-1. `escapeHtml`에 따옴표 이스케이프 누락 (보안)
- **파일**: `src/lib/wikiParser.js`
- **문제**: `escapeHtml`이 `&`/`<`/`>`만 이스케이프하고 `"`는 안 했음. 이 함수의 결과가 `data-doc-target="${...}"`, `alt="${...}"`처럼 큰따옴표로 감싼 HTML 속성 안에 그대로 들어가는 자리가 많은데, 그중 `resolved.target`(존재하지 않는 위키링크의 대상, 예: `[[없는문서]]`), `분류`/`틀`/`자료` 이름처럼 **사용자가 자유롭게 타이핑한 텍스트**가 들어가는 자리는 그 안에 `"`가 있으면 속성을 깨고 나와서 임의의 HTML 속성(`onmouseover=` 등)을 주입할 수 있었음.
- **재현**: 문서에 `[[없는문서"onmouseover=alert(1) x="y]]`라고 적으면 렌더링된 `<span>`에 실제로 `onmouseover` 속성이 붙어버림 (자기 자신의 문서에서만 실행되는 self-XSS 성격이지만, 렌더러가 `dangerouslySetInnerHTML`을 쓰는 이상 실제로 스크립트가 실행됨).
- **수정**: `escapeHtml`에 `.replace(/"/g, '&quot;')` 추가.
- **검증**: 위 문자열을 실제로 렌더링해서 `onmouseover` 속성이 안 생기는 것 확인.

### 1-2. 폴더 삭제 시 Windows 경로 구분자 불일치로 열린 문서가 안 닫힘
- **파일**: `src/store/useAppStore.js` (`deleteFile`)
- **문제**: 열려있는 문서가 지금 삭제하려는 **폴더 안에** 있는지 확인하는 코드가 `openPath?.startsWith(\`${filePath}/\`)`처럼 슬래시(`/`)만 확인했음. 실제 Windows 앱에서 경로는 백슬래시(`\`)로 오기 때문에(`path.join` 결과), 폴더를 삭제해도 그 안에 있던, 지금 열려있는 문서가 안 닫히고 에디터에 "삭제된 파일의 내용"이 그대로 남아있게 됨 — 그 상태로 편집을 계속하면 존재하지 않는 경로에 저장을 시도하게 됨. (브라우저 프리뷰의 mockApi는 경로에 `/`만 써서 이 버그가 안 보였음 — 실제 exe에서만 재현됨.)
- **수정**: `isPathUnder(child, parent)` 헬�퍼를 만들어 `/`와 `\` 둘 다 확인하도록 수정.

### 1-3. 계층형 분류(`포켓몬스터/전국도감`)의 설명 문서 생성이 크래시
- **파일**: `electron/fileSystem.js` (`ensureCategoryPage`, `scanCategoryPages`)
- **문제**: `buildAutoCategoryNames`(자동 분류 기능)는 "포켓몬스터/전국도감"처럼 슬래시가 들어간 계층형 분류 이름을 실제로 만들어냄. 그런데 `ensureCategoryPage`는 최상위 `.wikidesk-categories` 폴더만 만들고 그 안의 "포켓몬스터" 하위 폴더는 안 만든 채로 `전국도감.md`를 그 안에 쓰려고 해서 **`ENOENT` 에러로 크래시**함 — 해당 분류의 "분류 설명 문서 만들기" 버튼을 누르면 발생. 설령 이걸 고쳐도, `scanCategoryPages`가 최상위 폴더만 훑어봐서(하위 폴더 재귀 안 함) 만들어진 계층형 분류 페이지를 영영 못 찾는 문제도 같이 있었음.
- **수정**: `ensureCategoryPage`는 파일의 실제 부모 폴더까지 재귀적으로 생성하도록, `scanCategoryPages`는 하위 폴더까지 재귀적으로 훑어서 이름을 슬래시 포함 경로로 복원하도록 수정.
- **검증**: 실제 파일시스템(임시 폴더)에 대고 "포켓몬스터/전국도감" 분류 페이지를 만들고 다시 스캔해서 정상적으로 나오는 것까지 확인.

### 1-4. 문서/폴더 이름에 Windows 금지 문자를 쓰면 조용히 실패
- **파일**: `electron/fileSystem.js` (`createDoc`, `createFolder`, `renamePath`, `ensureDataEntry`, `ensureTemplate`, `renameImage`)
- **문제**: `< > : " / \ | ?  *`나 제어문자가 이름에 들어가면 Windows 파일시스템이 자체적으로 거부해서 `fs.writeFileSync`/`mkdirSync`/`renameSync`가 예외를 던지는데, 이걸 잡아서 사용자에게 알려주는 코드가 어디에도 없었음 — 새 문서/폴더를 만들거나 이름을 바꿀 때 이런 문자를 쓰면 **아무 반응 없이 조용히 실패**함. 세계관 노트 앱에서 "부제목: 내용"이나 "이유/결과"처럼 콜론·슬래시가 들어간 제목은 꽤 자연스럽게 나올 수 있는 입력이라 실사용에서 마주칠 가능성이 낮지 않음.
- **수정**: 금지 문자를 안전한 문자(`_`)로 바꿔주는 `sanitizeFileName` (일반 이름용)과 `sanitizeCategoryName`(슬래시는 계층 구분자라서 보존, 그 외 문자만 치환) 두 가지를 만들어 관련 함수들에 전부 적용. 이제 예외가 아예 안 나고, 대신 안전하게 치환된 이름으로 만들어짐.
- **검증**: 위 1-3 검증과 같은 스크립트에서 `질문? 부제: 이야기/모험`, `이야기<특수문자>테스트` 같은 이름으로 실제로 문서/폴더를 만들어서 정상 생성되는 것 확인.

### 1-5. 저장할 때마다 전체 재인덱싱이 두 번씩 실행되고, 워크스페이스를 바꿀 때마다 감시 리스너가 계속 쌓임
- **파일**: `src/store/useAppStore.js` (`loadWorkspace`)
- **문제 A**: `saveOpenFile`이 저장 직후 `rebuildIndexes()`를 직접 호출하는데, 그 저장 자체가 실제 파일 쓰기라서 chokidar 워처도 이걸 감지하고 `onWatchEvent` 콜백을 통해 **또 한 번** `rebuildIndexes()`를 호출함 — 타이핑을 멈출 때마다(자동저장) 전체 워크스페이스 재인덱싱이 두 번씩 실행됨.
- **문제 B (더 심각)**: `loadWorkspace`가 호출될 때마다(워크스페이스 전환 등) `onWatchEvent` 리스너를 새로 등록하는데, 이전 리스너를 해제하는 코드가 없었음. 워크스페이스를 세 번 전환하면 리스너가 3개 쌓여서, 그 이후로는 파일 하나가 바뀔 때마다 전체 재인덱싱이 3번씩 실행됨 — 세션 안에서 워크스페이스를 여러 번 바꿀수록 계속 나빠지는 누적 성능 문제.
- **수정**: 리스너를 등록하기 전에 이전 리스너를 먼저 해제(`unsubscribeWatch?.()`)하고, 워처가 감지한 변경은 400ms 디바운스를 걸어서 짧은 시간에 몰려오는 이벤트(저장 한 번에 여러 이벤트가 뜨는 경우 등)를 한 번의 재인덱싱으로 묶음.

### 1-6. `saveOpenFile`에서 `rebuildIndexes()` 호출에 `await` 누락
- **파일**: `src/store/useAppStore.js`
- **문제**: 그 자리만 `await` 없이 fire-and-forget으로 호출되고 있어서, 저장 직후 `rebuildIndexes()`가 실패하면 `catch` 블록에 안 잡히고 처리 안 된 프로미스 거부(unhandled rejection)로 콘솔에만 남음.
- **수정**: `await` 추가.

### 1-7. `decodeURIComponent`가 던지는 예외로 문서 전체 렌더링이 크래시할 수 있음
- **파일**: `src/lib/wikiParser.js`
- **문제**: 틀 관련 내부 플레이스홀더 토큰을 복원하는 자리에서 `decodeURIComponent`를 try/catch 없이 호출함. 실제로 이 토큰은 내부적으로 `encodeURIComponent`로 만들어지기 때문에 정상 흐름에서는 항상 안전하지만, 만약 사용자가 문서에 이 정확한 내부 토큰 문자열을 우연히(혹은 실험 삼아) 타이핑하면 `decodeURIComponent`가 예외를 던지고, 그 예외가 어디서도 안 잡혀서 **문서 전체 렌더링이 깨짐**(흰 화면까지는 아니어도 그 문서를 열 때마다 계속 실패).
- **수정**: try/catch로 감싸서 실패하면 인코딩된 원본 텍스트를 그대로 보여주도록 처리 — 일어날 확률은 매우 낮지만 고치는 비용도 매우 낮아서 처리함.

### 1-8. 새 문서/폴더 생성·이름 변경 실패 시 사용자에게 알림이 없었음
- **파일**: `src/App.jsx` (`handleCreateDoc`, `handleCreateFolder`, `handleRename`), `src/components/ImageSidebar.jsx` (`commitRename`)
- **문제**: 삭제(`handleDelete`)는 실패 시 `window.alert`로 알려주는데, 생성/이름변경은 그런 처리가 없어서 (1-4에서 다룬 금지 문자 문제가 아니더라도, 예를 들어 권한 문제 등으로) 실패하면 아무 반응이 없어 보였음.
- **수정**: 삭제와 동일한 패턴(try/catch + `window.alert`)을 생성/이름변경에도 적용.

### 1-9. 아무도 안 읽는 메타데이터 인덱스 시스템 제거
- **파일**: `electron/metadataIndex.js`(삭제), `electron/main.js`, `electron/preload.cjs`, `src/lib/mockApi.js`, `README.md`
- **문제**: `userData/index.json`에 문서마다 제목·태그·수정시각을 저장해두는 시스템이 있었는데, 문서를 저장/생성/삭제/이름변경할 때마다 (전체 JSON 파일을 읽고 고치고 다시 쓰는 식으로) 계속 갱신됐지만, **정작 이 인덱스를 읽어가는 코드가 앱 어디에도 없었음**(`getIndex()`를 호출하는 곳이 전무). 실제 검색 기능은 `useAppStore.js`가 워크스페이스 전체를 스캔해서 메모리에 만드는 별도의 `searchIndex`를 쓰고 있어서, 이 파일은 매번 디스크 I/O만 하고 아무 효과가 없는 죽은 코드였음.
- **조치**: `electron/metadataIndex.js` 삭제, 관련 호출부(main.js의 IPC 핸들러들, preload.cjs의 `getIndex`, mockApi.js의 `getIndex`) 전부 제거. README에도 이 사실과 이유를 남겨둠.
- **참고**: 실제로 파일 수가 아주 많아져서 매번 전체 스캔이 느려지는 시점이 오면, 그때 다시 제대로 된 영속 인덱스(SQLite 등)를 설계하는 게 나을 것 같음 — 지금 이 시스템을 그대로 되살리는 것보다는 새로 설계하는 편을 추천.

## 2. 알아두면 좋은 것 — 지금 당장은 문제 없지만 조건이 맞으면 터질 수 있는 것

이 항목들은 이번에 고치지 않았음(설계 재검토가 필요하거나, 실사용에서 마주칠 확률이 매우 낮거나, 지금 규모에서는 체감 안 되는 것들).

- **정규식 기반 인라인 파서는 `[[...]]`/`{{{...}}}` 중첩을 못 다룸**: `[[문서명|[[파일:...]]]]`처럼 링크 라벨 안에 또 다른 위키 문법을 넣는 건 전혀 지원 안 됨(나무위키 틀 재현 논의에서 이미 확인함, `docs/plans/image-links-and-colors.md` 참고). 이런 중첩을 넓게 지원하려면 지금의 "정규식으로 한 겹씩 치환" 구조를 실제 괄호 중첩을 추적하는 파서로 바꿔야 하는데, 이건 이 앱에서 가장 큰 구조 변경이 될 것.
- **제목/앵커 id 충돌**: 한 문서 안에 완전히 같은 제목이 두 개 있거나, `[anchor(이름)]`을 같은 이름으로 두 번 쓰면 둘 다 같은 HTML id를 갖게 되어 링크가 항상 첫 번째 것으로만 감. 실사용에서 마주칠 확률이 낮고, 고치려면 문서 전체를 한 번 더 스캔해야 해서(지금은 그럴 필요가 없는 게 장점) 의도적으로 그대로 둠.
- **내부 플레이스홀더 토큰과 사용자 텍스트 충돌**: `[목차]` 처리나 틀 관련 처리에 쓰는 `@@WIKIDESK_...@@` 형태의 내부 토큰을, 사용자가 문서에 그대로 타이핑하면(거의 있을 수 없는 일이지만) 렌더링이 꼬일 수 있음.
- **`rebuildIndexes()`가 매번 전체 워크스페이스를 다시 읽음**: 파일 하나만 바뀌어도 모든 문서를 다시 읽어서 인덱스를 처음부터 다시 만듦. 지금 규모(개인 세계관 노트, 수십~수백 문서)에서는 체감 안 되지만, 문서가 아주 많아지면(수천 개 이상) 이 부분이 느려질 수 있음 — 그때는 "바뀐 파일만 갱신"하는 증분 인덱싱으로 바꿔야 함.
- **`createWorkFolder`(작품 폴더 자동 스캐폴드)는 중간에 실패하면 롤백이 없음**: 디스크 용량 부족이나 권한 문제로 스캐폴드 생성 도중 실패하면, 이미 만들어진 폴더/문서는 그대로 남고 나머지는 안 만들어진 애매한 상태가 될 수 있음. 실사용에서 마주칠 확률이 매우 낮아서 자동 롤백까지는 구현 안 함 — 발생하면 남은 폴더를 수동으로 정리하면 됨.
- **CSS `light-dark()`/`@scope` 의존**: 라이트/다크 듀얼 컬러와 `{{{#!style}}}` 격리 기능이 비교적 최신 CSS 기능에 의존함. Electron이 최신 Chromium을 번들하는 이상 문제없지만, 혹시 아주 오래된 Electron 버전으로 내려가게 되면 재확인 필요.
- **금지 문자 치환이 완벽한 설명 없이 조용히 일어남**: 1-4에서 고친 건 "크래시하지 않게" 하는 것까지고, 예를 들어 `부제: 이야기`라고 입력하면 실제 파일명은 `부제_ 이야기`가 됨 — 사용자에게 "이 문자는 이렇게 바뀌었습니다"라고 알려주는 안내는 없음. 크래시보다는 훨씬 나은 상태지만, 더 다듬으려면 프롬프트 단계에서 미리 안내하는 것도 가능.

## 3. 앞으로 특정 기능이 생기면 문제가 될 만한 구조적 가정들

지금 코드베이스가 "당연하다"고 가정하고 있는 것들 — 아래 기능들이 실제로 추가된다면 이 가정들부터 깨질 것.

- **워크스페이스는 항상 하나뿐이라는 가정**: `electron/main.js`의 `watcher`/`currentWorkspacePath`, `useAppStore.js`의 `saveTimer`/`watchRebuildTimer`/`unsubscribeWatch`가 전부 모듈 전역 변수 하나씩임. "여러 워크스페이스를 동시에 열기"나 "창 여러 개" 같은 기능이 생기면 이 상태들을 워크스페이스/창 단위로 나눠야 함.
- **열려있는 문서는 항상 하나뿐이라는 가정**: `openPath`/`rawText`/`isDirty` 등이 전부 단일 값. "탭으로 여러 문서 동시 편집" 기능이 생기면 지금 구조로는 안 되고, 배열/맵 기반으로 다시 짜야 함.
- **동시 편집·충돌이 없다는 가정**: 저장은 항상 "지금 에디터에 있는 내용으로 덮어쓰기"뿐이라 병합/충돌 처리가 전혀 없음. 여러 기기나 사람이 같은 워크스페이스를 동시에 건드리는 기능(클라우드 동기화, 공유 등)이 생기면 이 부분을 통째로 새로 설계해야 함.
- **콘텐츠는 항상 본인이 직접 타이핑한다는 가정**: 이스케이프 처리는 이번에 보강했지만, 파서 전체가 "믿을 수 있는 사용자 자신의 입력"을 전제로 설계됨. 외부 소스에서 위키 문서를 가져오는 기능(URL 임포트, 공유받은 문서 열기 등)이 생기면 신뢰 경계가 달라지므로 전체 새니타이징을 다시 한번 점검해야 함.
