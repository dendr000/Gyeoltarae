# 나무위키 심화 문법 — 미구현 항목 구현 계획

- 참고 자료: [나무위키:문법 도움말/심화](https://namu.wiki/w/%EB%82%98%EB%AC%B4%EC%9C%84%ED%82%A4:%EB%AC%B8%EB%B2%95%20%EB%8F%84%EC%9B%80%EB%A7%90/%EC%8B%AC%ED%99%94)
- 작성일: 2026-09-15
- 목적: 심화 문법 도움말에 있는 항목들을 WikiDesk 현재 구현(`src/lib/wikiParser.js`, `README.md`)과 대조해서, 아직 없는 것들을 실제로 만들 때 어디를 건드려야 하는지 정리해 둔다. 이 문서 자체는 계획서이고, 실제 구현은 항목별로 별도 요청 시 진행한다.
- **진행 상황**: 1티어(0.42.0)·2티어(0.43.0) 전부 구현 완료. 아래 항목별 설명은 계획 당시 기록이라 지금 시점에서 "미구현"이라고 적힌 부분은 이미 구현됨 — 실제 동작은 README.md와 CHANGELOG.md 참고. 남은 건 3티어(선택적)뿐.

## 이미 구현되어 있는 것 (참고용, README.md와 동일)

`{{{#!folding}}}`, `{{{#!wiki style="..."}}}` (속성 화이트리스트 기반), 인라인 크기/색상(`{{{+N}}}`/`{{{#색상}}}`), 표 고급 속성(`<-N>`/`<|N>`/정렬/`bgcolor`/`rowbgcolor`/`colbgcolor`/`width`/`height`/`table*=` 전체 속성), 각주(`[* 내용]`, 번호 자동 매김), 자동 목차(`[목차]`, 항상 표시되는 플로팅 목차 포함), 구분선 4단계, 코드블록(`{{{ }}}`, 하이라이팅 없음), `[[분류:이름]]`, `{{틀:이름}}`/`[include(이름)]`(틀 공간 한정) — 여기까지는 손댈 필요 없음.

## 1티어 — 파서 로직만 확장하면 되는 것 (난이도 낮음, 실사용 가치 높음)

### 1-1. 각주 클릭 이동 (각주 앵커/역참조)
- **현재 상태**: `[* 내용]`이 `<sup class="wiki-footnote" data-footnote="N">N</sup>`으로만 렌더링됨 — 진짜 링크가 아니라서 클릭해도 아무 반응 없음. 각주 목록 쪽은 `<li id="fn-N">`까지는 있는데 본문으로 되돌아가는 링크가 없음.
- **나무위키 원문 동작**: 각주 번호를 누르면 `#fn-N`으로 스크롤 이동, 각주 항목에서 되돌아가기 화살표를 누르면 원래 읽던 위치로 복귀.
- **구현 방안**: `wikiParser.js`의 각주 렌더링을 `<sup><a href="#fn-N" id="fn-back-N">...</a></sup>`로, 각주 목록 항목에 `<a href="#fn-back-N">↩</a>`를 추가. 이건 그냥 `<a href="#...">`라서 브라우저 기본 스크롤로 동작 — 별도 클릭 핸들러 불필요.
- **영향 범위**: `wikiParser.js`만.

### 1-2. 표 캡션
- **현재 상태**: 없음.
- **나무위키 문법**: 표 위/아래에 제목을 붙이는 문법(`|캡션|`).
- **구현 방안**: 표 블록 바로 앞/뒤 줄이 `|텍스트|` 형태면 캡션으로 인식해서 `<caption>` 또는 표 위/아래 `<div class="wiki-table-caption">`로 렌더링. `renderTable` 호출 전후로 별도 라인 검사 추가.
- **영향 범위**: `wikiParser.js`의 표 처리 부분(`parseWikiText`의 테이블 버퍼링 로직, `renderTable`).

### 1-3. 표 셀 패딩 제거 단축 속성 (`<nopad>`)
- **현재 상태**: 없음. 이미지/영상을 셀에 꽉 채우려면 `<width=...><height=...>`만 가능하고 안쪽 여백은 못 없앰.
- **구현 방안**: `parseTableCell`의 `<...>` 속성 파싱에 `nopad` 토큰 하나 추가해서 해당 셀에 `padding:0` 인라인 스타일 부여.
- **영향 범위**: `wikiParser.js`의 `parseTableCell`/셀 렌더링.

### 1-4. `{{{#!wiki lang="ko/ja/zh"}}}`
- **현재 상태**: 없음.
- **구현 방안**: `{{{#!wiki}}}` 헤더 파싱 정규식에 `lang="..."` 속성을 추가로 뽑아서, 짧은 언어 코드 화이트리스트(`ko`/`ja`/`zh`/`en` 등)에 있을 때만 렌더링되는 `<div>`에 `lang="..."` 속성으로 그대로 붙임. CSS 자체는 건드릴 필요 없음(브라우저가 `lang` 속성 보고 알아서 폰트/줄바꿈 처리).
- **영향 범위**: `wikiParser.js`의 `wikiStyleMatch` 처리 부분.

### 1-5. `{{{#!wiki tag="span"}}}` (블록 대신 인라인 태그로)
- **현재 상태**: `{{{#!wiki style="..."}}}`는 항상 `<div>`로 렌더링됨 — 문장 중간에 인라인으로 스타일 박스를 쓰고 싶어도 강제 줄바꿈됨.
- **구현 방안**: 헤더에서 `tag="span"` 같은 속성을 뽑아서, 태그 이름 화이트리스트(`span`, `div`, `a`는 href 없는 형태로만 등 최소한만) 안에서 골라 쓰게 함.
- **영향 범위**: `wikiParser.js`.

### 1-6. 스타일 속성 화이트리스트 소폭 확장
- **현재 상태**: `ALLOWED_STYLE_PROPS`에 웬만한 건 다 있음(색/배경/테두리/여백/크기/폰트/`float`/`display`/`opacity`). `word-spacing`, `text-transform`, `filter`(blur 등 안전한 값만) 정도가 비어 있음.
- **구현 방안**: 필요할 때마다 `ALLOWED_STYLE_PROPS`에 한 줄씩 추가 + `sanitizeStyleValue`에 위험한 값(예: `filter: url(...)`) 막는 조건만 같이 추가. 급한 건 아니고, 실제로 막혀서 불편한 사례가 나오면 그때 추가하는 쪽을 추천.
- **영향 범위**: `wikiParser.js`.

## 2티어 — 새로운 렌더링 개념이 필요한 것 (중간 난이도)

### 2-1. 문서 내/문서 간 특정 위치로 이동하는 링크
- **나무위키 문법**: `[anchor(이름)]`으로 임의 지점에 이름표를 붙이고, `[[#이름]]`(같은 문서) / `[[문서명#이름]]`(다른 문서) 또는 `[[문서명#제목]]`(그 문서의 특정 목차 항목)으로 그 지점까지 스크롤 이동.
- **현재 상태**: 완전히 없음. `applyInline`의 위키링크 파싱은 `#` 뒤를 그냥 문서명의 일부로 취급해서 엉뚱한 이름으로 `docIndex`를 찾게 됨. 제목에는 이미 `slugifyHeading` 기반 `id`가 붙어 있어서(플로팅 목차가 이걸로 스크롤함) 같은 문서 안에서 제목으로 점프하는 건 절반은 준비돼 있음.
- **구현 방안**:
  1. 위키링크 타겟 파싱 시 `#` 기준으로 `문서명`과 `앵커`를 분리.
  2. `앵커`가 있으면: 문서명이 비어 있으면(=`[[#이름]]`) 현재 문서, 있으면 `docIndex`로 대상 문서를 찾음.
  3. `[anchor(이름)]` 매크로 자체는 `<span id="anchor-이름"></span>`으로 렌더링(별도 인라인 문법 추가, `applyInline`에 정규식 하나).
  4. 앵커가 제목 텍스트와 일치하면 기존 `slugifyHeading` id를 그대로 재사용, 아니면 `anchor-이름` id를 찾음.
  5. 클릭 시 "다른 문서 열기 + 그 앵커까지 스크롤"은 렌더링만으론 안 되고 `ViewerPane.jsx`에 로직 추가 필요: 문서를 연 다음 `requestAnimationFrame`으로 해당 id 엘리먼트를 `scrollIntoView` 호출.
- **영향 범위**: `wikiParser.js`(파싱), `ViewerPane.jsx`(문서 전환 후 스크롤).

### 2-2. 편집기 전용 숨김 노트 (`## 내용`, `##@ 내용`)
- **나무위키 문법**: 그 줄이 편집 화면에서만 보이고 실제 렌더링에는 전혀 안 나타나는 메모. `##@`는 편집 페이지 맨 위에 고정 표시.
- **현재 상태**: 없음 — 지금은 `##`으로 시작하는 줄도 그냥 일반 텍스트로 렌더링됨(단, `#태그` 줄 감지 정규식과 헷갈리지 않는지도 같이 확인 필요).
- **구현 방안**: `parseWikiText`의 줄 처리 루프 맨 앞에서 `##`로 시작하는 줄은 렌더링 결과에서 완전히 제외(에디터의 원문에는 당연히 그대로 남음 — 렌더러만 건너뜀). `##@`는 일단 `##`과 동일하게 숨기는 것부터 시작하고, "편집 페이지 상단 고정 표시" 같은 나무위키 특유의 문서-히스토리 UI는 WikiDesk에 그런 개념 자체가 없어서 그대로 가져올 필요는 없어 보임.
- **영향 범위**: `wikiParser.js`.

### 2-3. 전역 스타일 선언 + 클래스 재사용 (`{{{#!style}}}`, `{{{#!wiki class="..."}}}`, `<rowclass=>`/`<tableclass=>`)
- **나무위키 문법**: 문서 어딘가에서 `{{{#!style .badge { background: gold; } }}}`처럼 CSS 클래스를 한 번 선언해두면, 문서 안 어디서든 `{{{#!wiki class="badge"}}}`나 표 셀의 `<rowclass=badge>`/`<tableclass=badge>`로 재사용 가능.
- **현재 상태**: 없음. 지금 `{{{#!wiki style="..."}}}`는 매번 그 자리에서 인라인 스타일을 직접 쓰는 방식뿐이라, 같은 스타일을 여러 군데 쓰려면 매번 복사-붙여넣기 해야 함.
- **구현 방안**: 이건 지금까지의 "인라인 스타일 화이트리스트 필터링"과는 결이 달라서 더 신중해야 함 — CSS 선택자/블록 자체를 파싱해서 `<style>` 태그로 문서에 주입하는 구조라, 클래스 이름은 반드시 `/^[a-zA-Z][\w-]*$/` 같은 화이트리스트로 제한하고, 선택자도 클래스 선택자(`.이름`)만 허용해서 임의 셀렉터(예: `body`, `#app` 등 앱 전역에 영향 주는 것)로 스타일이 새 나가지 않게 막아야 함. 속성 값 자체는 기존 `sanitizeStyleValue`를 재사용. 문서마다 매번 파싱하면 비용이 있으니 `parseWikiText` 안에서 한 번만 스캔해서 모으는 방식 추천.
- **영향 범위**: `wikiParser.js` 전반적으로 새 파싱 단계 추가, `ViewerPane.jsx`(문서 렌더링에 `<style>` 삽입 지점 필요 — `dangerouslySetInnerHTML`에 함께 넣을지 별도 `<style>` 태그로 분리할지 결정 필요).
- **참고**: 표의 `<rowclass=>`/`<tableclass=>`는 이 시스템이 먼저 있어야 의미가 있어서 같이 묶어서 진행하는 걸 추천.

### 2-4. 코드블록 문법 강조 (`{{{#!syntax 언어}}}`)
- **현재 상태**: `{{{ }}}`는 있지만 항상 그냥 모노스페이스 플레인 텍스트.
- **구현 방안**: 실제 하이라이팅을 하려면 하이라이팅 라이브러리(예: `highlight.js`, `prismjs`)가 필요한데, WikiDesk는 완전 로컬/오프라인 앱이라 CDN 로드가 아니라 `npm install`로 번들에 포함시켜야 함(패키징 용량이 좀 늘어남 — 언어 문법 정의를 필요한 것만 골라 넣으면 완화 가능). 최소 버전으로는 언어 이름만 `<pre data-lang="js">`처럼 표시해두고, 실제 색칠은 별도 라이브러리 도입 여부를 먼저 정하고 진행하는 걸 추천.
- **영향 범위**: `wikiParser.js`, `package.json`(새 의존성), 패키징 용량.

## 3티어 — 설계 고민이 필요한 것 (선택적, 우선순위 낮음)

### 3-1. 클릭 인터랙션 (탭, 다중 필터, `onclick`으로 클래스 토글)
- **나무위키 문법**: `{{{#!wiki onclick="..."}}}`로 클릭 시 클래스를 추가/제거/토글해서 탭 UI나 필터링 목록을 만듦.
- **현재 상태**: 없음. WikiDesk 렌더러는 완전히 정적인 HTML만 만들어서 문서 자체에 동작(behavior)이 붙는 개념이 아예 없음.
- **왜 신중해야 하는지**: `onclick` 속성을 문서 원문에서 그대로 HTML로 흘려보내는 건 렌더링에 `dangerouslySetInnerHTML`을 쓰는 지금 구조상 절대 안 됨(임의 스크립트 실행 경로가 열림). 만들게 되면 "클래스 토글"이라는 딱 한 가지 동작만 허용하는 안전한 미니 문법(예: `data-toggle-target="선택자" data-toggle-class="이름"`)으로 별도 설계하고, 실제 이벤트 리스너는 React 쪽(`ViewerPane.jsx`)에서 그 데이터 속성만 보고 붙여야 함 — 나무위키 문법을 1:1로 베끼는 게 아니라 같은 결과(탭/토글)를 안전하게 내는 WikiDesk 자체 문법을 새로 정의하는 셈이라, 문법 설계부터 다시 논의하고 시작하는 걸 추천.
- **영향 범위**: `wikiParser.js`, `ViewerPane.jsx`, 보안 검토.

### 3-2. 페이지 수 매크로 (`[pagecount]`)
- **나무위키 문법**: 전체 문서 수(또는 특정 분류 소속 문서 수)를 표시.
- **WikiDesk에서의 의미**: "사이트 전체 문서 수" 개념이 없고 워크스페이스 단위라, `docIndex`/`categoryIndex` 크기를 세는 정도로 대체 가능. 실사용 가치가 낮아 보여서 우선순위는 낮음.

## 이미 의도적으로 제외하기로 한 것 (README.md 명시, 이번 조사로 재확인만 함)

`#redirect`, `[math(...)]`, `[youtube(...)]`, `[ruby(...)]`, `[age(...)]`, `[dday(...)]` — README.md의 "의도적으로 제외한 문법" 절에 이미 이유가 적혀 있음. 이번 심화 문법 조사에서 새로 나온 것 중에서는 없었고, 그대로 유지하는 걸 추천. 필요해지면 개별로 논의해서 추가.

## 구조적으로 해당 없음 (나무위키와 워크스페이스 구조 자체가 달라서)

- `[[\문자]]`, `[[문서명:(/경로)]]`처럼 `/`, `|`, `#`, `]` 같은 특수문자가 든 문서명을 다루는 이스케이프 문법: 나무위키는 모든 문서가 하나의 평평한 이름공간이라 `/`가 "하위문서"라는 특별한 의미를 가져서 이런 이스케이프가 필요함. WikiDesk는 실제 파일시스템 폴더/파일 구조를 그대로 쓰기 때문에 애초에 이 문제가 발생하지 않음 — 구현 대상에서 제외.

## 추천 진행 순서

1티어(1-1 ~ 1-6)는 각각 독립적이고 작아서 원하는 순서대로 아무거나 먼저 요청해도 됨. 2티어는 2-1(문서 내 이동)이 실사용 가치가 제일 크고, 2-3(전역 스타일)은 2-1보다 설계 비용이 커서 뒤에 두는 걸 추천. 3티어는 실제로 필요한 구체적인 사례(예: "이런 탭 UI를 만들고 싶다")가 생기면 그때 문법을 같이 설계하는 게 나을 것 같음.
