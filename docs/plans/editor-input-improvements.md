## 용어 설명

- **textarea**: 웹 화면의 기본 여러 줄 입력칸. 결타래 편집기는 이것 하나로 글을 입력받는다. 줄마다 따로 색을 칠하거나 줄 앞에 표시를 붙이는 기능이 기본으로 없다.
- **배경판(backdrop)**: 지금 제목 강조를 위해 textarea 뒤에 겹쳐 둔, 글자가 투명한 똑같은 텍스트. 이 배경판에서 제목 줄에만 색을 칠한다. 두 요소가 같은 위치·같은 줄바꿈이어야 막대가 맞는다.
- **줄바꿈 표시(wrap)**: 한 줄이 너무 길어 화면 끝에서 다음 줄로 접혀 보이는 것. 글 한 줄(논리 줄)이 화면에서는 여러 줄(시각 줄)로 보일 수 있다.
- **IME**: 한글처럼 글자를 조합해서 입력하는 방식. 조합 중에는 `e.key` 가 자모로 오거나 키 이벤트가 평소와 달라서, 키 가로채기가 가장 많이 깨지는 곳이다.
- **`e.code` / `e.key`**: 키 이벤트의 두 이름. `e.code` 는 물리적 키 위치(`Minus`, `NumpadSubtract`), `e.key` 는 입력되는 글자(`-`, `+`). 배열이 달라도 `e.code` 는 키 자리 그대로다.
- **원자 단위(atomic)**: 커서가 안쪽으로 들어갈 수 없는 한 덩어리. 방향키 한 번에 통째로 건너뛰고, 지울 때도 통째로 지워지는 것.
- **순수 함수 모듈(`src/lib/*.js`)**: 화면 없이 입력→출력만 계산하는 파일. 이 프로젝트는 편집 규칙을 여기에 두고 `tests/lib/` 에서 시험한다(예: `codeFence.js`, `lineDuplicate.js`, `tableNav.js`). 새 기능도 같은 방식으로 한다.

## 공통 구현 원칙 (6건 모두)

1. 규칙 계산은 `src/lib/` 의 새 순수 함수 모듈에 넣고, `EditorPane.jsx` 의 `handleKeyDown` 은 호출만 한다. 이미 `EditorPane.jsx` 가 매우 길다(Tab 처리는 1051줄 근처).
2. 글을 바꾸는 동작은 반드시 기존 `replaceRange()` (내부적으로 `execCommand('insertText')`)를 거친다. 그래야 Ctrl+Z 한 번으로 되돌아간다. 직접 `textarea.value = ...` 로 바꾸지 않는다.
3. 한글 입력 조합 중(`e.isComposing`)에는 새 키 처리를 건너뛴다. 판정은 `e.key` 만이 아니라 `e.code` 도 함께 본다(이전에 한글 상태에서 키가 자모로 오는 문제가 있었다).
4. 상용구/파일 추천 팝업이 열려 있을 때는 기존 팝업 키 처리가 먼저다(`handleKeyDown` 앞쪽 882, 918줄 블록). 새 처리는 팝업이 없을 때만 동작한다.
5. 테스트: 순수 함수는 경계값 포함 단위 테스트, 키 처리는 미리보기에서 **실제 키 입력**으로 확인한다(콜백 직접 호출 시험은 클릭·키 버그를 못 잡는다는 이전 교훈). 구현 후 변이 검사(조건을 일부러 틀리게 해서 테스트가 실패하는지)도 한다.
6. 문서: 기능마다 `docs/features/기능명.md`, `docs/CHANGELOG.md`(기능 추가 = MINOR +1), 필요 시 README 기능 목록, 오류를 만나면 `docs/troubleshooting.md`.

## 1. 목록 줄 Enter 이어쓰기

### 가능 여부
가능. 현재 목록 줄 이어쓰기 동작이 전혀 없으므로(Enter 처리는 위키링크 탈출 하나뿐) 새로 넣는 것이고, 기존 동작과 부딪히는 지점이 적다.

### 정확한 동작 (제안 그대로 + 확인할 가장자리 규칙)
- 커서가 `* 문장` 줄 끝에서 Enter → 아래 줄이 `* ` 로 시작한다. 들여쓰기가 있으면(`    * 문장`) 같은 들여쓰기를 이어받는다.
- 자동으로 생긴 `* ` 만 있는 줄(내용 없음)에서 Enter → 그 줄의 `* ` 가 지워져 빈 줄이 된다(목록 종료). 들여쓰기만 남기지 않는다.
- 커서가 줄 **중간**에 있을 때 Enter → 커서 뒤 글자가 새 줄의 `* ` 뒤로 내려간다(VS Code 목록 편집기와 같은 방식). 줄 맨 앞(마커 앞)에서 Enter 는 일반 줄바꿈.
- 코드블록(```) 안에서는 동작하지 않는다(`isInsideCodeFence` 재사용).
- 대상: `*` 목록(`LIST_RE`)만. 번호 목록(`1.`)과 인용(`>`)은 요청 범위 밖이므로 이번에 넣지 않고 "나중에 같은 모듈에 규칙만 추가" 로 남긴다.
- 선택 영역이 있으면(범위 선택 후 Enter) 이어쓰기 없이 일반 동작.

### 설계
- 새 파일 `src/lib/listContinue.js`: `listContinueEdit(value, selStart, selEnd)` → `null`(일반 Enter) 또는 `{ from, to, insert, caret }`. 기존 `fenceAutoCloseEdit` 와 같은 반환 모양으로 맞춘다.
- `EditorPane.jsx`: 위키링크 Enter 처리 **뒤**, 일반 키 처리 앞에 `e.key === 'Enter'` 분기를 추가한다. 수정/Shift+Enter/Ctrl+Enter 는 제외(Shift+Enter 로 목록 항목 안에서 줄바꿈하는 용도를 남길 수 있음 — 확인 필요).
- 마커 정규식은 `wikiParser.js` 의 `LIST_RE` 와 어긋나지 않게 **같은 상수를 내보내 재사용**하는 쪽이 안전하다(구현 시 해당 상수가 export 되는지 확인).

### 주의할 점 / 위험
- 팝업(상용구/파일)이 열려 있을 때 Enter 는 후보 확정이므로 먼저 처리돼야 한다. 팝업이 없는데 상용구 `{#}` 커서 자리와 겹치는지도 본다.
- 표(`||`) 편집기 모달은 별개 화면이라 영향 없음.
- 한글 조합 중 Enter 는 조합 확정이므로 `e.isComposing` 이면 건드리지 않는다. 확정 후 다시 Enter 를 치면 그때 동작.

### 단계
1. `listContinue.js` + 테스트(일반/들여쓰기/중간 분할/빈 항목 제거/코드블록/선택 영역/마커 없는 줄/줄 맨 앞).
2. `handleKeyDown` 연결, 미리보기에서 실제 Enter·Ctrl+Z·한글 입력 확인.
3. 문서·CHANGELOG(MINOR).

예상 규모: 작음(파일 2~3개).

## 2. 굵게(`'''`) 바깥으로 커서 이동 + 원자 단위 취급

### 현재 동작(읽어서 확인한 부분)
- Ctrl+B: `wrapSelection(textarea, "'''", "'''", onChange)` 로 선택을 `'''…'''` 로 감싸고 안쪽 글자를 다시 선택해 둔다.
- 손으로 `'` 를 치면 `AUTO_PAIRS` 때문에 `''` 쌍이 자동으로 생긴다. **사용자 결정(2026-10-08): 손으로 `'` 를 하나씩 쳐서 굵게를 만드는 경우는 이번 범위에서 제외한다.** 기능은 Ctrl+B 경로에만 적용한다.

### 2-a. Ctrl+B 후 닫는 `'''` 오른쪽 바깥으로 커서 두기 — 가능
- **글을 선택하고 Ctrl+B**: `'''선택한글'''` 로 감싼 뒤 커서를 닫는 `'''` **바로 오른쪽 바깥**에 둔다(지금은 안쪽 글자가 선택된 상태로 남는다). 이어서 바로 다음 글을 쓸 수 있다.
- **선택 없이 Ctrl+B**: 글을 써야 하므로 `'''|'''` 처럼 가운데에 커서를 둔다. 다 쓴 뒤 → 키 한 번(아래 2-b)으로 닫는 `'''` 바깥으로 나온다. 이 경우도 바깥에 두길 원하는지 구현 전에 확인한다(가운데에 두는 것이 입력에 필요하다고 판단해 이렇게 적었다).
- 확인할 것: `wrapSelection` 이 이미 감싸진 글에 Ctrl+B 를 다시 눌렀을 때 벗기는(토글) 동작이 있는지. 있다면 "안쪽 선택이 남는 현재 동작" 에 기대고 있는 것이므로, 바깥 커서로 바꾸면 토글이 깨지는지 구현 전에 읽어서 확인하고 테스트에 넣는다. (이 문서를 쓰는 중에는 확인하지 않았다.)

### 2-b. `'''` 를 한 덩어리로 — 부분 가능
textarea 는 글자 단위로만 커서를 움직이므로 "원래 한 덩어리" 로 만들 수는 없고, **키 입력을 가로채서** 비슷하게 만든다.

| 키 | 규칙 | 가능성 |
|---|---|---|
| → | 커서 바로 오른쪽이 `'''` 이면 3칸 이동 | 가능 |
| ← | 커서 바로 왼쪽이 `'''` 이면 3칸 이동 | 가능 |
| Backspace | 커서 바로 왼쪽이 `'''` 이면 3글자 삭제 | 가능 |
| Delete | 커서 바로 오른쪽이 `'''` 이면 3글자 삭제 | 가능 |
| Shift+←/→ | 선택 끝을 3칸씩 확장 | 가능하나 `selectionDirection` 처리가 필요해 구현이 번거로움 |
| Ctrl+←/→ (단어 이동) | 원래 동작 유지 | 건드리지 않음 |
| 마우스 클릭 | `'''` 사이에 커서가 놓일 수 있음 | **막을 수 없음**(클릭은 가로채지 못한다) |

- 위험 1: `''''` (따옴표 4개) 처럼 `'''` 가 겹쳐 보이는 문자열에서 "어디까지가 `'''` 인지" 모호하다. 규칙: 정확히 3개가 연속된 경우만 덩어리로 보고, 4개 이상 연속이면 기존 글자 단위 동작.
- 위험 2: 이탤릭(`''`)과의 경계. `''`+`'''` 가 붙은 `'''''굵은 기울임'''''` 에서도 오동작하지 않게 "3개 연속" 판정을 앞뒤 글자까지 보고 한다.
- 위험 3: 이 규칙은 `'''` 가 굵게 표기가 **아닌** 곳(코드블록, 일반 글 속 따옴표 세 개)에서도 켜지면 방해가 된다. 코드블록 안에서는 끄고(`isInsideCodeFence`), 나머지 경우는 허용한다.
- 위험 4: 한글 조합 중에는 끈다(`e.isComposing`).
- "안 되면 말고" 기준으로 보면: ←/→/Backspace/Delete 네 개는 확실히 되고, Shift 확장과 마우스 클릭은 불완전한 상태로 남을 수 있다. 이 한계를 문서에 적는다.

### 2-c. Tab 의 공백 4칸을 한 덩어리로 — 가능(방식 선택)
지금 Tab 은 공백 4칸(`'    '`)을 넣는다(`EditorPane.jsx` 1051줄 근처). 한 덩어리처럼 보이게 하는 방법이 둘이다.

| 방식 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A (추천) | 공백 4칸 유지. **줄 맨 앞 들여쓰기** 구간에서만 ←/→/Backspace/Delete 가 4칸 단위로 움직이고 지운다 | 파일 내용·파서가 그대로. 이미 들여쓰기 깊이를 4칸 단위로 계산(`listDepthByIndent`)해서 일관됨 | 4의 배수에서 어긋난 들여쓰기(공백 2칸 등)는 "남는 칸부터" 처리하는 규칙이 필요. 마우스 클릭은 못 막음 |
| B | 진짜 탭 문자(`\t`) 한 글자를 넣고 CSS `tab-size: 4` 로 4칸 너비로 보이게 함 | 원래 한 글자라 방향키·삭제가 자연스럽게 한 번에 됨 | 이미 저장된 문서(공백 4칸)와 섞이고, 복사·붙여넣기·검색·코드블록 내용·표 등에서 탭이 새로 등장해 예기치 못한 곳이 생김. 파서는 `\t` 를 4칸으로 보지만(`listDepthByIndent`) 다른 정규식들이 탭을 처리하는지 전수 확인 필요 |

- 결정 요청: **방식 A 로 진행** 을 추천한다(파일 형식을 바꾸지 않는다).
- A 의 세부 규칙: 커서가 줄 앞 공백 구간 안에 있고, 커서 왼쪽(또는 오른쪽)에 공백이 4칸 이상 연속이면 4칸 단위로 이동/삭제. 4칸 미만이면 남은 만큼. 줄 중간 공백(단어 사이)은 건드리지 않는다.

### 설계
- 새 파일 `src/lib/atomicTokens.js`: `atomicMove(value, pos, dir)`, `atomicDelete(value, pos, dir)` 가 `{ from, to }` 또는 `null` 반환. 토큰 종류(`'''`, 줄 앞 4칸 공백)를 배열 하나로 두어 나중에 `~~`·`__` 같은 것도 추가할 수 있게 한다.
- `handleKeyDown`: 팝업 처리 뒤, `selectionStart === selectionEnd`(선택 없음)일 때만 동작. 선택이 있으면 기본 동작.
- 이동은 `setSelectionRange`(글이 안 바뀌므로 undo 영향 없음), 삭제는 `replaceRange`.

### 단계
1. `wrapSelection` 을 읽어 Ctrl+B 의 현재 동작(토글 여부 포함)을 확인하고, 미리보기에서 Ctrl+B 결과를 재현해 기록. (손으로 `'` 를 치는 경우는 범위 밖.)
2. `atomicTokens.js` + 테스트(3개 연속/4개 연속/경계/줄 앞 공백/줄 중간 공백/코드블록).
3. 키 연결 + 실제 키 입력 확인(한글 상태 포함).
4. 문서.

예상 규모: 중간. 2-b·2-c 는 같은 모듈이라 함께 하는 편이 낫다.

## 3. 숫자패드 `-` / `+` → Home / End

### 질문에 대한 답: 서로 다른 키인가?
**다르다.** 키보드 이벤트에서 `e.code` 가 숫자패드 `-` 는 `NumpadSubtract`, 숫자패드 `+` 는 `NumpadAdd`, 글자 오른쪽 위의 `-` 는 `Minus`, `+` 는 Shift+`Equal` 로 구분된다. 그래서 숫자패드 쪽만 따로 가로채는 것이 가능하다. 숫자패드 `-`/`+` 는 NumLock 이 꺼져 있어도 같은 코드가 온다(바뀌는 건 숫자 키들뿐).

### 가능 여부
가능하고 매우 쉽다. 단, **숫자패드가 없는 노트북에서는 누를 키 자체가 없어서 이 기능이 도움이 되지 않는다.** "노트북에는 Home/End 가 없어서" 라고 하셨으므로 아래를 확인해야 한다.

- **사용자 결정(2026-10-08)**: 노트북 자체 키보드용이고 Home/End 키가 없다. 그래서 **Alt+←/→ 를 줄 처음/끝(Home/End)** 으로 쓴다. 숫자패드 `-`/`+` 는 외장 키보드에서도 쓰고 싶을 때를 위한 덤으로 같이 넣을지 선택(기본은 넣지 않음 — NumLock 켠 숫자패드로 `-`/`+` 입력하는 용도를 뺏지 않으려고).
  - Alt+Shift+←/→ 는 줄 처음/끝까지 선택으로 확장(VS Code 의 Shift+Home/End 와 같음).
  - 충돌 확인(코드 읽음): 편집기의 기존 Alt 단축키는 Alt+Enter, Alt+H, Alt+Shift+H, Ctrl+Shift+Alt+- 뿐이라 Alt+방향키와 겹치지 않는다. 브라우저의 "뒤로 가기" 기본 동작은 Electron 창에서 일어나는지 구현 전에 미리보기 대신 실제 앱에서 한 번 확인한다(`preventDefault` 로 막으면 해결되는 문제).
  - 줄바꿈 표시(wrap)된 긴 줄에서는 논리 줄 기준으로 움직인다(한계로 문서화).
- 숫자패드를 가로채면 NumLock 이 켜진 상태에서 숫자패드로 `-`, `+` 를 **입력하는 용도**를 잃는다. 제안: 숫자패드 `-`/`+` 를 눌렀을 때 Home/End 로 동작하되, 설정 토글("숫자패드 -/+ 를 Home/End 로 사용")을 두고 기본은 켜짐으로 한다. 토글 위치는 기존 설정 화면.
- 기존 `Ctrl+Shift+Alt+(Minus|NumpadSubtract)` 취소선 단축키(1046줄)와 부딪히지 않게 **수정키 없이** 눌렀을 때만 Home/End 로 동작시킨다. Shift+숫자패드 `-`/`+` 는 "줄 처음/끝까지 선택" 으로 확장 가능(요청 범위 밖이므로 선택 사항).

### 설계
- 새 순수 함수는 필요 없고(`lineBounds(value, pos)` 정도), `handleKeyDown` 에 분기 하나. 줄바꿈 표시(wrap)된 줄에서 Home/End 는 시각 줄 기준이 일반적인데, 직접 구현하면 논리 줄 기준이 된다 → **합성 키 이벤트로 진짜 Home/End 를 발생시킬 수 없으므로** 논리 줄 기준 이동이 된다는 한계를 문서화하거나, 기존 `withCaretMirror` 측정 기법으로 시각 줄 끝을 찾는다. 추천: 1차는 논리 줄 기준.

예상 규모: 매우 작음.

## 4. 여러 줄 선택 + Tab 들여쓰기 (VS Code 방식)

### 현재 상태
Tab 은 어디서나 선택 영역을 공백 4칸으로 **바꿔 쓴다**(선택한 글이 사라진다. Ctrl+Z 로는 복구된다). 코드블록 전용 Tab 처리는 따로 없다.

### 가능 여부
가능, 쉬운 편.

### 정확한 동작
- 선택이 **여러 줄에 걸쳐 있으면**(줄바꿈 하나라도 포함): 선택에 걸친 모든 줄 앞에 공백 4칸을 붙이고, 선택은 줄 전체를 유지한 채 확장 표시한다(VS Code와 동일).
- **Shift+Tab**: 걸친 모든 줄 앞에서 공백 최대 4칸(또는 탭 1개)을 제거. 공백이 없는 줄은 그대로.
- 선택 마지막 줄에서 선택 끝이 그 줄 **맨 앞**(0번째 칸)이면 그 줄은 대상에서 제외(VS Code 규칙. 안 그러면 줄 전체를 선택하려다 다음 줄까지 들여쓰는 일이 생긴다).
- 선택이 **한 줄 안**이거나 없으면 지금처럼 4칸 공백 삽입(현재 동작 유지). Shift+Tab 만 줄 앞 4칸 제거를 추가(선택 없이도 현재 줄 내어쓰기) — 이 부분은 요청에 없던 것이라 선택 사항이며, 넣는다면 문서에 명시.
- 팝업이 열려 있으면 Tab 은 후보 확정이므로 기존 처리가 우선.

### 설계
- 새 파일 `src/lib/lineIndent.js`: `indentLinesEdit(value, selStart, selEnd, outdent)` → `{ from, to, insert, selStart, selEnd }`. 줄 경계 계산은 `lineDuplicate.js` 의 "선택에 걸친 줄" 로직과 겹칠 수 있으니 재사용 가능한지 먼저 본다(확인 필요).
- 글 변경은 한 번의 `replaceRange` 로 해서 Ctrl+Z 가 한 번에 되돌린다.
- 변경 후 선택 범위를 `requestAnimationFrame` 안에서 복원(기존 Ctrl+D/코드 펜스 처리와 같은 패턴).

### 위험
- 줄 수가 매우 많을 때 `execCommand('insertText')` 로 큰 덩어리를 넣는 성능(수천 줄은 드묾 — 구현 후 1000줄 선택으로 확인).
- 2-c 와 맞물림: 들여쓰기가 공백 4칸 단위로 유지돼야 2-c 의 "4칸 덩어리" 이동이 맞는다.

예상 규모: 작음.

## 5. 최상위 폴더 범위 영어 단어 자동 추천

### 가능 여부
가능. 이유: 앱이 열 때 모든 문서의 내용을 메모리에 들고 있다(`useAppStore.js` 의 `searchIndex[path] = { content, aliases }`, `rebuildIndexes` 에서 생성). 그러므로 별도 파일 읽기 없이 단어를 뽑을 수 있다. 상용구 자동 추천 팝업 구조(`findSnippetQuery`, 후보 `rank`)에 후보를 얹는 형태가 가장 단순하다.

### "범위" 정의 (사용자 결정 2026-10-08 반영)
예시가 `웹툰 → 멸망 이후의 세계`, `강의 → 따즈아` 로 **둘 다 작업공간 바로 아래 폴더(최상위 폴더)의 하위 폴더(두 번째 단계 폴더)**다. 기존 코드의 `findWorkFolderContext` 는 소설/웹툰/만화와 포켓몬스터만 인식하고 `강의` 는 모르므로 쓰지 않고, 폴더 위치만으로 범위를 정한다.

- **기본 범위 = 두 번째 단계 폴더**(`강의/따즈아`, `웹툰/멸망 이후의 세계`, `소설/이런 영웅은 싫어`). 현재 편집 중인 문서가 속한 두 번째 단계 폴더 안의 문서에서 나온 단어만 후보가 된다. 최상위 폴더 바로 아래에 문서가 직접 있으면(두 번째 단계 폴더가 없으면) 그 최상위 폴더 자체가 범위.
- **포함 범위 선택(체크 표시)**: 최상위 폴더마다 "이 폴더 전체 문서에서 단어 모으기" 체크를 둔다.
  - 꺼짐(기본): 두 번째 단계 폴더 안의 문서만. 예) `따즈아` 에서 쓴 단어는 `따즈아` 의 다른 문서에서만 뜬다.
  - 켜짐: 그 최상위 폴더 아래 모든 문서(`강의` 전체)에서 모은 단어가 `강의` 안의 어느 문서에서든 뜬다.
  - 위치 제안: 이미 있는 상용구 모달의 "폴더별 사용" 탭(`SnippetFolderTab.jsx`)과 같은 곳에 "단어 추천 범위" 구역을 만들어, 최상위 폴더 목록 + 체크박스를 둔다. 저장 방식은 `snippetScope.js` 의 `disabledFolders` 와 같은 모양(최상위 폴더 이름 배열, 예 `wholeFolderScopes`)을 제안한다. 같은 곳에서 단어 추천 전체를 켜고 끄는 체크도 둔다.
  - 확인 필요: 이 체크를 상용구 모달 탭에 둘지, 폴더 우클릭 메뉴/설정에 둘지(기본 제안은 상용구 모달 탭).

### 정확한 동작
- 단어 추출: 영문자로 시작하고 영문자·숫자·`_` 로 이어지는 3글자 이상(`CREATE`, `employee_id`). 한글은 대상 아님. 코드블록 안의 단어는 포함(SQL 예시가 주 용도).
- 같은 단어의 대소문자 변형은 **가장 많이 쓰인 모양**을 대표로 하고, 검색은 대소문자 무시 접두어(기존 상용구 규칙과 동일하게 `C` → `CREATE`).
- 순서: 상용구 후보가 먼저, 그 다음 폴더 단어(많이 쓴 순). 이미 같은 이름의 상용구가 있으면 중복 후보를 올리지 않는다.
- 지금 입력 중인 단어 자신이 후보에 뜨는 문제 방지: 현재 문서에서 방금 친 글자가 색인되면 `Cre` 가 후보 `Cre` 가 된다 → "정확히 같은 철자만 있는 후보는 제외" 및 "2번 이상 쓰인 단어만 또는 다른 문서에서 나온 단어만" 중 하나로 처리. 추천: **저장된 파일 내용 기준 색인**이므로 아직 저장 전 입력은 색인에 없지만, 자동 저장이 곧 반영돼 같은 문제가 생길 수 있으니 "현재 문서에서만 나온 단어는 제외" 규칙을 둔다.
- 팝업에서 구분되게 표시(예: 분류 칸에 `단어(따즈아)`).
- 켜고 끄기: 이미 있는 "폴더별 사용" 탭(`SnippetFolderTab.jsx`, `snippetScope.js` 의 `disabledFolders`)과 같은 방식으로 "범위 단어 추천 사용" 체크를 한 곳에 두는 것을 제안(기본 켜짐). 설정 위치는 구현 전에 확인.

### 설계
- 새 파일 `src/lib/scopeWords.js`: `scopeOfPath(path, rootPath)`(최상위 폴더와 두 번째 단계 폴더 이름을 돌려줌), `extractWords(text)`, `buildScopeWordIndex(searchIndex, rootPath)` → 두 번째 단계 폴더별 `{ [범위]: [{ word, count }] }`, 테스트 포함. "최상위 폴더 전체" 가 켜진 경우는 같은 최상위 폴더의 두 번째 단계 색인들을 합쳐(빈도 합산) 쓰므로 색인은 한 벌만 만들고 조회 때 합친다(합친 결과는 캐시).
- 테스트에 넣을 경우: 두 번째 단계 폴더가 둘인 최상위 폴더에서 체크 꺼짐/켜짐 결과 비교, 최상위 폴더 바로 아래 문서(두 번째 단계 폴더 없음), 다른 최상위 폴더 단어가 섞이지 않음.
- `useAppStore.js`: `rebuildIndexes` 끝에서 `scopeWordIndex` 를 만들어 상태에 저장(`searchIndex` 가 이미 계산된 직후라 추가 파일 읽기 없음). 비용은 전체 글 한 번 훑는 정도 — 작업공간이 큰 경우를 대비해 구현 후 `D:\WikiDesk` 규모로 시간을 잰다.
- `EditorPane.jsx`: 상용구 후보를 만드는 곳에서 현재 문서의 범위 단어를 가상 항목으로 합친다. 코드블록 안의 `wordStartOnly`, Enter 로 확정하지 않는 규칙(`enterAcceptsSuggestion`)은 그대로 적용된다.

### 위험
- 후보가 너무 많아져 상용구를 밀어낼 수 있다 → 표시 개수 상한, 상용구 우선.
- 영어 비율이 낮은 작품 폴더(웹툰 설정 글)에서는 쓸모가 거의 없음 → 기본 켜짐 대신 "코드블록 안에서만" 같은 제한도 가능(결정 필요).
- 갱신 시점: 색인은 파일 변경 때 다시 만들어지므로 방금 쓴 단어가 몇 초 늦게 반영될 수 있다.
- 대안(이미 가능): 폴더별 상용구 폴더를 직접 만드는 방식은 지금도 쓸 수 있다(SQL 묶음처럼). 이 기능은 그 수작업을 없애는 것이다.

예상 규모: 중간.

## 6. 제목 강조 막대 어긋남 + 줄 여백(점 토글)

### 사용자가 알려 준 증상 (2026-10-08)
"강조 표시가 문단(=) 줄에 생기지 않고 엉뚱한 줄에 생김. 한 줄 아래나 위, 몇 칸 떨어진 곳의 줄." → **어긋나는 정도가 한 줄에서 몇 줄까지 제각각**이다. 이는 아래 가설 1(긴 줄이 두 요소에서 서로 다르게 접혀 줄 수 차이가 쌓임)과 맞다: 긴 줄이 한두 개면 한 줄 어긋나고, 많은 구간을 지나면 몇 줄로 커진다. 반대로 가설 4(소수 픽셀 오차)는 문서 아래로 갈수록 천천히 커지는 모양이라 "한 줄 위로"(음수 방향)가 나오기 어렵다. 진단 1단계에서 이 판단을 실제로 측정해 확인한다.

### 줄 번호 (사용자 결정, 2026-10-08)
줄 번호가 있으면 좋겠다고 했으므로 6-2 단계의 줄 여백에 **줄 번호를 함께 둔다.** 거슬리지 않게:
- 글자 크기는 본문보다 작게(예: 본문 대비 85%), 색은 본문 글자색보다 훨씬 옅게(라이트/다크 모두 대비를 낮게, 색 토큰으로 한 곳에서 관리).
- 평소에는 옅게 보이고, 줄 위에 마우스를 올리거나 현재 커서가 있는 줄만 조금 진하게.
- 줄 번호 표시는 켜고 끄는 설정(기본 켜짐)을 둔다.
- 줄바꿈된 긴 줄은 번호를 첫 시각 줄에만 표시(나머지는 비움).
- 번호 열의 폭은 문서의 줄 수 자릿수에 맞춰 고정(자릿수가 바뀔 때 본문이 흔들리지 않게 최소 3자리 폭).

### 지금까지 상황
- 구조: `textarea` 뒤에 투명한 배경판을 겹쳐 두고 배경판의 제목 줄에만 색을 칠한다(`App.css` 의 `.editor-highlight-backdrop`, `.editor-heading-highlight-line`).
- 이전에 두 번 고쳤다. (1) 스크롤 위치 강제 동기화(불완전), (2) 제목 span 안의 `\n` 이 빈 줄을 하나 더 만들던 문제 제거(`docs/troubleshooting.md` 2026-10-02 항목). 그 뒤에도 어긋난다고 하셨고, 이 문서를 쓰는 작업에서는 첨부 이미지를 볼 수 없어서 **어긋나는 상황(어떤 문서, 어느 위치, 긴 줄이 있는지)을 확인하지 못했다.**

### 원인 가설 (확인 전)
1. **스크롤바 폭 차이**: `textarea` 는 아래 여백(`--editor-tail`) 때문에 항상 세로로 스크롤되어 스크롤바 폭만큼 글 영역이 좁다. 배경판은 `overflow: hidden` 이라 스크롤바가 없어 글 영역이 더 넓다. 그러면 **화면 너비에 닿는 긴 줄(줄바꿈 표시)이 서로 다른 지점에서 접혀** 줄 수가 달라지고, 그 뒤의 막대가 모두 밀린다. 긴 줄이 많은 문서일수록 심해지고 짧은 줄만 있으면 멀쩡해 "가끔" 어긋나는 증상과 맞는다.
2. 한글/영문 혼합 줄에서 두 요소의 글꼴 대체(fallback)가 달라 폭이 다르게 계산될 가능성(같은 `font` 선언이라 가능성은 낮음).
3. 한글 조합 중 임시 글자가 `textarea` 에는 있고 배경판 상태에는 아직 없는 짧은 시간(다음 렌더에서 맞춰짐, 일시적).
4. 창 크기·확대 비율이 소수점일 때 줄 높이(`14px*1.7`)가 반올림되어 줄이 쌓일수록 어긋나는 오차.

→ **1단계는 먼저 진단**이다. 아래 순서로 한다.

### 6-1단계: 진단과 고치기 (오버레이 유지, 추천 첫 작업)
1. 미리보기에서 긴 줄(화면보다 긴 줄) 여러 개 + 제목이 섞인 문서를 만들고, `textarea.clientWidth` 와 배경판 `clientWidth`, 두 `scrollHeight` 를 JS 로 비교한다(차이가 있으면 가설 1 확정).
2. 가설 1 이 맞으면: 두 요소에 `scrollbar-gutter: stable` 을 주거나 배경판을 `overflow-y: scroll`(스크롤바는 투명하게)로 해서 글 영역 폭을 같게 만든다. Electron(Chromium) 은 `scrollbar-gutter` 를 지원한다(구현 전 버전 확인).
3. 소수 픽셀 오차(가설 4)는 줄 높이를 `px` 정수(예: 24px)로 고정해 확인한다. 줄 높이가 1.7배라 23.8px 이 되는 점이 의심스럽다 → 정수 높이로 바꾸면 쌓이는 오차가 없어진다(글자 모양 변화 가능성은 확인).
4. 이후 **자동 검사**를 만든다: 임의의 긴 글에서 `textarea.scrollHeight === backdrop.scrollHeight` 가 항상 같은지(여러 너비에서) 확인하는 점검 스크립트. 단위 테스트(node 환경)로는 못 하므로 미리보기 점검 절차로 문서화.
5. 문서/troubleshooting 기록.

성공 기준: 긴 줄·한글·여러 제목이 섞인 문서를 끝까지 스크롤해도 막대가 항상 제목 줄과 겹친다.

### 6-2단계: 줄 여백(점 토글) — 부분 가능
**제안 동작**: 각 줄 왼쪽에 줄 여백을 두고, 줄 위에 마우스를 올리면 맨 왼쪽에 점이 나타나며, 점을 누르면 그 줄이 강조된다. 제목(`=`) 줄은 자동으로 "켜짐" 상태.

- 가능한 이유: 줄 여백도 배경판과 같은 방식(글 영역과 같은 크기의 보이지 않는 사본)으로 각 줄의 위치·높이를 얻어 그릴 수 있다. **그러나 6-1단계의 어긋남 문제가 해결되지 않으면 점도 같은 방식으로 어긋난다.** 그래서 6-1 이 먼저다.
- 줄바꿈된 긴 줄: 점은 **논리 줄의 첫 시각 줄**에만 표시하고, 강조는 그 논리 줄 전체 높이에 칠한다(배경판이 이미 이 방식).
- 마우스를 올린 줄 판정: `textarea` 위의 `mousemove` 좌표를 줄 위치 표와 비교(`textarea` 가 맨 위라 아래 요소는 이벤트를 못 받는다). 줄 여백 영역은 `textarea` 바깥 왼쪽에 둔다.
- **켠 상태를 어디에 저장하나 — 결정 필요**:
  - 제목 줄: 자동이라 저장 불필요.
  - 일반 줄을 수동으로 켠 것: 줄 번호는 편집하면 밀린다. 선택지 (a) 저장하지 않고 문서를 열어 둔 동안만 유지(편집 시 줄 번호를 보정), (b) 파일에 표시를 남김(예: 줄 끝 특수 표기) → 문서 내용·파서에 영향이 커서 비추천, (c) 별도 사이드 파일에 줄 내용 해시와 함께 저장 → 복잡. **(a) 를 추천.**
- 줄 번호 표시는 요청에 없었으므로 점만 만든다(원하면 같은 여백에 줄 번호를 쉽게 얹을 수 있다).

### 6-3단계: 편집기 교체(CodeMirror 6 등) — 이번에는 하지 않는 것
- 줄 단위 장식·줄 여백·강조를 가장 안정적으로 제공하는 정석 방법이지만, 지금 `EditorPane.jsx` 의 자동 괄호 쌍, 상용구 팝업의 커서 좌표 계산, 표 편집기 연동, 코드블록 처리, Ctrl+D, 한글 조합 처리 등이 모두 `textarea` 기준으로 쓰여 있어 **사실상 편집기를 다시 만드는 규모**다. 번들 크기도 늘어난다.
- 판단 기준: 6-1 을 마쳐도 어긋남이 남거나 6-2 의 점이 만족스럽지 않을 때만 별도 계획서로 다룬다.

### 위험 요약
- 원인을 확인하지 않고 점 기능부터 만들면 같은 어긋남이 점에도 생긴다.
- 6-2 는 마우스 이벤트가 많아 성능(긴 문서) 확인이 필요하다. 줄 위치 표는 글이 바뀔 때만 다시 계산한다.

예상 규모: 6-1 작음~중간(진단 포함), 6-2 중간~높음.

### 이번 한도(약 13%)에 대한 제안
- **1~3번(Alt+←/→, 여러 줄 Tab, 목록 이어쓰기)** 을 한 묶음으로 하는 것을 추천한다. 모두 순수 함수 + 키 분기 한 곳 구조라 서로 독립이고, 하나씩 커밋하면 한도가 끊겨도 완성된 것만 남는다.
- **7번(6-1)** 은 이전에 두 번 못 잡은 문제라 체감이 가장 크지만 측정 단계가 예상보다 길어질 수 있다. 1~3번을 마치고 한도가 남을 때 **진단만 먼저** 하고, 수정은 원인이 확정되고 수정이 작을 때만 이어서 하는 식을 제안한다.
- 나머지(5, 6, 8번)는 다음 한도에 새 채팅에서 이 계획서를 시작점으로 한다.

### AI 의견: 추가로 권하는 것
- **들여쓰기 단위를 한 곳에 모으기**: Tab(항목 4)·목록 이어쓰기(항목 1)·4칸 덩어리(항목 2-c)·파서(`listDepthByIndent`)가 모두 "들여쓰기 한 칸 = 공백 4칸" 을 가정한다. 상수(`INDENT_UNIT = 4`)를 `src/lib/` 의 작은 모듈에 두고 모두 거기서 가져오면, 나중에 바뀌어도 한 곳만 고치면 된다. 1~3번을 구현할 때 같이 하면 비용이 거의 없다.
- **Shift+Tab 은 선택이 없어도 현재 줄 내어쓰기**: VS Code 와 같아서 낯설지 않다(항목 4에 선택 사항으로 적어 둠, 추천).
- **어긋남 점검 스크립트**: 항목 6-1 에서 만드는 "입력칸과 배경판 높이 비교" 를 개발용 스크립트로 남기면, 이후 CSS 를 고칠 때 회귀를 바로 알 수 있다.
- **막대 어긋남 임시 완화책**: 6-1 전에도 쓸 수 있는 방법으로, 편집 모드에서 줄바꿈 표시를 꺼서(가로 스크롤) 긴 줄을 접지 않으면 어긋남의 원인(줄 접힘 차이)이 사라진다. 긴 글을 쓰기에는 불편하므로 선택 옵션으로만 제안한다.
